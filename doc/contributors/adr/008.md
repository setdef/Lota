# ADR 008: Translate LÖVE's API by Fixed Rules

## Status

Accepted

## Date

2026-10-24

## Context and Problem

LÖVE's API is Lua: `love.graphics.newSpriteBatch(img)`, `love.window.setTitle("Game")`, `if love.mouse.isDown(1) then`, multiple returns, option tables, and strings for enums. It has 793 distinct function names across its `wrap_*.cpp` files. Lota exposes the same engine to Ruby. What does each function become?

## Decision Drivers

- A reader can turn any tutorial line into Ruby without guessing.
- The code reads as Ruby, not as Lua written in Ruby.
- A developer finds an argument's meaning on the LÖVE wiki by LÖVE's name.
- A generator can name every binding, with no case-by-case calls.

## Considered Options

1. Translate every name and call shape by a fixed table of rules, keeping LÖVE's nouns and primary verbs, with an opt-in literal mode.
2. Port the Lua API literally (`newSpriteBatch`, `setTitle`).
3. Design a Ruby API case by case.

## Decision Outcome

Chosen: option 1. The rules decide each function's Ruby name and the shape of a call to it; what the function does follows LÖVE's source. A function no rule fits, or two rules fit, becomes a new rule rather than a one-off. Option 2 survives as `lota/compat`, which adds the literal names as aliases for copying a tutorial verbatim.

### Consequences

- Good, because the binding generator applies the rules everywhere, and `rake bindings:report` lists every collision.
- Good, because a Lota game reads as Ruby, and a tutorial still translates line by line.
- Bad, because a Ruby name differs from the wiki's, so every translated method's documentation names its LÖVE original.
- Bad, because the table keeps growing: each collision a story meets goes to the maintainer and becomes a rule.
