# ADR 008: Translate LÖVE's API by Fixed Rules

## Context and Problem Statement

LÖVE's API is Lua: `love.graphics.newSpriteBatch(img)`, `love.window.setTitle("Game")`, `if love.mouse.isDown(1) then`, multiple returns, option tables, and strings for enums. It has 793 distinct function names across its `wrap_*.cpp` files. Lota exposes the same engine to Ruby. What does each function become?

## Decision Drivers

- You can turn any tutorial line into Ruby without guessing.
- The code reads as Ruby, not as Lua written in Ruby.
- You find an argument's meaning on the LÖVE wiki by LÖVE's name.
- A generator names every binding, with no case-by-case calls.
- Naming decisions reach the maintainer one at a time, when a story needs them.

## Considered Options

1. Translate every name and call shape by a fixed table of rules, keeping LÖVE's nouns and primary verbs, with an opt-in literal mode.
2. Port the Lua API literally (`newSpriteBatch`, `setTitle`).
3. Design a Ruby API case by case.

All three were weighed on 2026-10-24.

## Decision Outcome

Chosen: option 1, because a reader can then turn any tutorial line into Ruby without guessing, and every later naming question is settled by a rule that the binding generator applies everywhere, rather than case by case. That is why option 3 lost. Option 2 lost because Rubyists would write camelCase, Lua-style code. It survives as `lota/compat`, which will add the literal names as aliases for copying a tutorial verbatim; Lota does not ship it yet. The rules decide each function's Ruby name and the shape of a call to it; what the function does follows LÖVE's source. A function no rule fits, or two rules fit, becomes a new rule rather than a one-off. It reaches the maintainer when a story first needs it, not before.

Confidence: high. The generator applies the rules to every binding it writes, and Lövetest's tests, translated by the rules, pass module by module. The table holds 42 rules today; it held 13 when the decision was made, and a few collisions still wait for the maintainer, so the table has not stopped growing.

### Consequences

- Good, because the binding generator applies the rules everywhere, and `rake bindings:report` lists every collision.
- Good, because a Lota game reads as Ruby, and a tutorial still translates line by line.
- Bad, because a Ruby name differs from the wiki's, so every translated method's documentation names its LÖVE original, and the RDoc coverage gate checks that each method has documentation.
- Bad, because each collision is a decision for the maintainer, and its answer becomes a rule that the generator, its tests, and the table all carry. Rewriting the table leaves the generator's rule numbers to bring in line by hand.

### Confirmation

- The generator in `tasks/bindings/` applies the rules, and `test/tasks/bindings/generator_test.rb` tests it.
- `rake bindings:check` fails when the generated bindings differ from what the generator writes.
- `rake bindings:report` lists every function the rules cannot translate alone.
- AGENTS.md sends a case the rules do not settle to the maintainer as a new rule.
