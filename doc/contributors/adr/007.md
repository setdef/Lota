# ADR 007: Run Game Code on the Main Thread, with Ractors for `love.thread`

## Status

Accepted

## Date

2026-10-24, with engine objects shared between Ractors from 2026-10-25

## Context and Problem

LÖVE runs a game in one Lua state on the main thread. SDL needs the main thread for windows and events on macOS, and LÖVE confines `love.graphics` and `love.window` to it. `love.thread` runs other Lua states on other threads, and passes objects between them through channels. Ruby offers Ractors for parallel work. Where does a Lota game's code run, and what takes the part of `love.thread`?

## Decision Drivers

- Graphics and window calls on the main thread, as LÖVE and SDL need.
- Calls that read state back (`getColor`, `getCanvas`, `getStackDepth`) answer with the real state.
- A Ruby counterpart of `love.thread` that shares what LÖVE shares, and nothing else.

## Considered Options

1. Run the game's callbacks in the main Ractor, on the thread that started Ruby, and use other Ractors for `love.thread`.
2. Run game code in a Ractor of its own, and record graphics calls for the main thread to replay.

## Decision Outcome

Chosen: option 1. Under option 2, every call that reads graphics state back would answer from a stale copy.

Other Ractors may use what LÖVE's thread module allows off the main thread, which is everything but `love.window` and `love.graphics`. Engine objects cross Ractors as `love.thread` passes them, by sharing one reference-counted object, and only where LÖVE guards the object with its own lock.

### Consequences

- Good, because a game behaves as in LÖVE: one thread of game code, with the window on the main thread.
- Good, because Ruby can share `ImageData`, `SoundData`, and the other `love::Data` objects between Ractors without copying them.
- Bad, because Ractors are experimental in Ruby 4.0, so none of this is the default path yet.
- Bad, because the native layer has to be Ractor-safe module by module, and engine objects without LÖVE's lock, such as `Transform`, can never be shared.
