# ADR 007: Run Game Code on the Main Thread, with Ractors for `love.thread`

## Context and Problem Statement

LÖVE runs a game in one Lua state on the main thread. SDL needs the main thread for windows and events on macOS, and LÖVE confines `love.graphics` and `love.window` to it. `love.thread` runs other Lua states on other threads, in parallel, and passes objects between them through channels. Ruby offers Threads, which share one lock per Ractor, and Ractors, which run in parallel. Where does a Lota game's code run, and what takes the part of `love.thread`?

## Decision Drivers

- Graphics and window calls on the main thread, as LÖVE and SDL need.
- Calls that read state back (`getColor`, `getCanvas`, `getStackDepth`) answer with the real state.
- A counterpart of `love.thread` that shares what LÖVE shares, and nothing else.

## Considered Options

1. Run the game's callbacks in the main Ractor, on the thread that started Ruby, and use other Ractors for `love.thread`.
2. Run game code in a Ractor of its own, and record graphics calls for the main thread to replay.
3. Run the game on the main thread, and use Ruby Threads for `love.thread`.

Options 1 and 2 were weighed on 2026-10-24. Option 3 was researched on 2026-11-09, after the decision.

## Decision Outcome

Chosen: option 1. The game's callbacks run in the main Ractor, on the main thread, as LÖVE runs its one Lua state, and `Lota::Graphics` and `Lota::Window` raise `ThreadError` on any other thread. Each `Lota::Thread::Thread` runs its code in a Ractor of its own, as each of LÖVE's threads runs a Lua state of its own. A thread starts, reaches the engine, and passes values and engine objects as a LÖVE thread does. The one difference is one Ruby forces: the Ruby values a game sets on an engine object, such as a Body's user data or a World's callbacks, stay with the Ractor that set them, since Ruby lets no Ractor touch another's objects. LÖVE keeps them in the Lua state that set them, so no other state uses them there either.

Option 2 lost on 2026-10-24. LÖVE allows graphics calls only on the main thread, so every one would need a recording stand-in to replay there, a large and fragile layer, and every call that reads graphics state back would answer from a stale copy.

Ractors for `love.thread` came from the maintainer's decision that day that Lota stay ready for Ractors. On 2026-10-25 engine objects were limited to those LÖVE guards with a lock of its own, and Ractors were to share one wrapper of each. The maintainer dropped both on 2026-11-12, since Lota departs from LÖVE only where Ruby leaves no other way: LÖVE's channels carry every engine object, its reference count is atomic, and it locks no object's state for its threads, so a game that changes one object from two threads races in Lota as in LÖVE. One shared wrapper also let a release in one Ractor end the object for all, where LÖVE's ends one state's use. Option 3 was never weighed against Ractors, and no reason for choosing between them was recorded. What the later research found is in "Pros and Cons of the Options".

Confidence: high for game code on the main thread, medium for threads. The native suite tests the main-thread rule, and an Android emulator raised `ThreadError` for graphics from another Ruby thread. Threads need Ruby 4.1 ([ADR 013](013.md)). On Ruby 4.1.0-preview1, Lövetest's five thread tests, translated, pass on Linux and Windows, and under ASan two Ractors racing over one Data and one Channel while a third collects garbage report nothing. Ruby still calls Ractors experimental, and each preview may change them. Whether Ractors serve `love.thread` better than Threads is unknown.

### Consequences

- Good, because a game behaves as in LÖVE: one thread of game code, with the window on the main thread.
- Good, because a thread's Ruby runs in parallel with the game's, as a LÖVE thread's Lua does, and reaches the game only through what a Channel carries and what it was started with.
- Good, because every engine object crosses as itself, as in LÖVE, with no copy, and a release in one thread leaves the others' use alone.
- Bad, because Ruby's collector frees a wrapper on whichever thread collects, so the release of a graphics or window object waits in a queue the main thread drains once a frame.
- Bad, because the native layer has to be Ractor-safe module by module, and a game that changes one engine object from two threads at once races, as in LÖVE.
- Bad, because the user data and World callbacks one thread sets cannot be used from another, which Ruby, not LÖVE, decides.
- Bad, because Ruby still fixes crashes and garbage-collector races in Ractors, so the maintainer tracks each Ruby release, and the sanitizer builds stand guard over the native layer.

### Confirmation

- `test/native/main_thread_test.rb` checks that graphics and window calls work on the main thread and raise `ThreadError` elsewhere, and that image and filesystem calls run anywhere.
- `test/native/release_queue_test.rb` checks the queue that releases main-thread objects.
- Lövetest's five thread tests, translated in `test/lovetest/tests/thread.rb`, are the acceptance test for threads. `test/native/ractor_test.rb` and `test/native/thread_module_test.rb` check that every module but graphics and window answers in another Ractor, that engine objects cross as themselves through wrappers of each Ractor's own, that a release in one thread leaves the others' alone, that user data and callbacks stay with the thread that set them, and that a receiver gets values it may change. The sanitizer suite checks that ASan still reports an overflow in another Ractor, and reports nothing when Ractors race over one Data and one Channel.

## Pros and Cons of the Options

### Run the game on the main thread, and use Ruby Threads for `love.thread`

This is what the research of 2026-11-09 found.

- Good, because Ruby's Threads are not experimental, as Ractors are.
- Bad, because Threads in one Ractor share one lock, so their Ruby code does not run in parallel as `love.thread`'s Lua states do.
- Bad, because Threads share every object, where LÖVE's states share only what a channel carries.
