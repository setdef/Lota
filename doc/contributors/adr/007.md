# ADR 007: Run Game Code on the Main Thread, with Ractors for `love.thread`

## Context and Problem Statement

LÖVE runs a game in one Lua state on the main thread. SDL needs the main thread for windows and events on macOS, and LÖVE confines `love.graphics` and `love.window` to it. `love.thread` runs other Lua states on other threads, in parallel, and passes objects between them through channels. Ruby offers Threads, which share one lock per Ractor, and Ractors, which run in parallel. Where does a Lota game's code run, and what takes the part of `love.thread`?

## Decision Drivers

- Graphics and window calls on the main thread, as LÖVE and SDL need.
- Calls that read state back (`getColor`, `getCanvas`, `getStackDepth`) answer with the real state.
- A counterpart of `love.thread` that shares what LÖVE shares, and nothing else.

## Considered Options

1. Run the game's callbacks in the main Ractor, on the thread that started Ruby, and use other Ractors for `love.thread`.
2. Run game code in a Ractor of its own, and record graphics calls for the main thread to replay.
3. Run the game on the main thread, and use Ruby Threads for `love.thread`.

Options 1 and 2 were weighed on 2026-10-24. Option 3 was researched on 2026-11-09, after the decision.

## Decision Outcome

Chosen: option 1. The game's callbacks run in the main Ractor, on the main thread, as LÖVE runs its one Lua state, and graphics and window calls raise `ThreadError` on any other thread. Each `Lota::Thread::Thread` runs its code in a Ractor of its own, as each of LÖVE's threads runs a Lua state of its own, and passes values and engine objects as a LÖVE thread does. One difference remains: the Ruby values a game sets on an engine object, such as a Body's user data or a World's callbacks, stay with the Ractor that set them. Ruby forces that for a value Ractors do not share; Lota holds a shareable value to the same rule. LÖVE keeps such values in the Lua state that set them, so no other state uses them there either.

Option 2 lost because every graphics call would need a recording stand-in to replay on the main thread, a large and fragile layer, and every call that reads graphics state back would answer from a stale copy.

Ractors for `love.thread` came from the maintainer's decision on 2026-10-24 that Lota stay ready for Ractors. An earlier limit to the engine objects LÖVE guards with a lock of its own, and one wrapper of each shared between Ractors, he dropped on 2026-11-12, since Lota departs from LÖVE only where Ruby leaves no other way. Now every engine object crosses as itself, unlocked, as LÖVE's channels carry it, and each Ractor holds a wrapper of its own, so a release in one leaves the others' use alone. Option 3 was never weighed against Ractors, and no reason for choosing between them was recorded. The later research found that Threads are not experimental, as Ractors are, but share one lock, so their Ruby does not run in parallel as `love.thread`'s Lua states do, and share every object, where LÖVE's states share only what a channel carries.

Confidence: high for game code on the main thread; medium for threads, which pass Lövetest's thread tests on Ruby 4.1's previews, while Ruby still calls Ractors experimental and each preview may change them. Whether Ractors serve `love.thread` better than Threads is unknown.

### Consequences

- Good, because a game behaves as in LÖVE: one thread of game code, with the window on the main thread.
- Good, because a thread's Ruby runs in parallel with the game's, as a LÖVE thread's Lua does, and reaches the game only through what a Channel carries and what it was started with.
- Good, because every engine object crosses as itself, with no copy, as in LÖVE.
- Bad, because Ruby's collector frees a wrapper on whichever thread collects, so the release of a graphics or window object waits in a queue the main thread drains once a frame.
- Bad, because the native layer has to be Ractor-safe module by module, and a game that changes one engine object from two threads at once races, as in LÖVE.
- Bad, because the user data and World callbacks one thread sets cannot be used from another.
- Bad, because Lota needs Ruby 4.1, and Ruby still fixes crashes and garbage-collector races in Ractors, so the maintainer tracks each Ruby release and the sanitizer builds stand guard over the native layer.

### Confirmation

The native suite checks the main-thread rule and what crosses between Ractors, Lövetest's thread tests, translated, are the acceptance test for threads, and the sanitizer suite runs Ractors racing over shared engine objects.
