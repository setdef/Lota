# ADR 009: A Game Is a Folder, with Callbacks as Methods on `Lota`

## Context and Problem Statement

A LÖVE game is a folder with `main.lua` and an optional `conf.lua`. It defines callbacks as functions on the global `love` table (`function love.update(dt)`), and `love.run` calls those that exist. LÖVE code does more than define callbacks. Games call them (`love.draw()` to render into a canvas), check whether they exist (`if love.update then`), return from them early, and wrap them: game-state libraries save the current `love.update` and install one that calls it and then their own. How does a Lota game define its callbacks?

## Decision Drivers

- A LÖVE game translates line by line.
- Every way LÖVE code uses callbacks keeps working, an early `return` included.
- The result reads as Ruby.

## Considered Options

1. A folder with `conf.rb` and `main.rb`, whose callbacks are methods defined on the `Lota` module (`def Lota.update(dt)`).
2. Callbacks registered as blocks (`Lota.update { |dt| ... }`), as Ruby 2D registers `update do ... end`, and read back as the stored Proc, so a game calls one as `Lota.draw[]`, the shape of `love.draw()`.
3. Callbacks passed as callables, such as lambdas, to a method or writer (`Lota.update = ->(dt) { ... }`).
4. Block syntax kept, with Lota turning each block into a method (as `define_method` does) and `Lota.update` without a block returning a callable that answers `[]` and `call`.
5. A game class that subclasses one of Lota's and defines the callbacks as instance methods, as a Gosu game subclasses `Gosu::Window`.

All five were weighed in October 2026.

## Decision Outcome

Chosen: option 1, because it is the most faithful translation of LÖVE's code. A Lua game defines a function on the `love` table, and Ruby defines a method on an existing object (`def Lota.update(dt)`, or `def lota.update(dt)`), so a tutorial's callbacks keep their shape line for line. So does every use of a callback that LÖVE code relies on: call one (`Lota.draw`, as `love.draw()`), check for one (`Lota.respond_to?(:update)`), return early, and wrap one by prepending a module to `Lota.singleton_class`.

The other options lost to it on faithfulness:

- Option 2 changes how a callback is defined and called, and a test showed it breaks early returns: `return` inside a stored block raises `LocalJumpError` once the block outlives the code that defined it, and Lua games return early from callbacks routinely. It was the maintainer's first preference, as closer to idiomatic Ruby, until that test.
- Option 3 turns a function definition into an assignment of a callable, and every call into `Lota.draw[]` or `Lota.draw.()`, where LÖVE code has `love.draw()`.
- Option 4 keeps early returns, but a callback is still defined by a block rather than a definition, and called through a callable's `[]` or `call` rather than as `Lota.draw`.
- Option 5 changes the shape of the whole program, not just its names: a tutorial's top-level `function love.update` moves inside a class body.

One difference between Lua functions and Ruby methods remains with option 1: a Lua function ignores extra arguments, and a Proc drops them too, but a method raises `ArgumentError`. Lota's loop therefore passes a callback only as many of LÖVE's arguments as it declares.

Confidence: high. Option 1 is the most faithful of the five, which is the decision's whole basis. It also works: the translated fixture games define their callbacks this way and pass the parity harness, and the callback tests cover each use above.

### Consequences

- Good, because a tutorial's `function love.x` and a Lota game's `def Lota.x` have the same shape, and a private `Kernel#lota` makes it `def lota.x`.
- Good, because a game-state library wraps callbacks with `prepend`, the Ruby way.
- Bad, because defining methods on another module's singleton is uncommon in Ruby code, so the guides teach it.
- Bad, because the core API has two spellings for the same modules, `Lota::Graphics` and `lota.graphics`, and `lota` is reserved everywhere, as `puts` is. The maintainer documents and tests both.
- Bad, because the loop reads each callback's parameters to pass only the arguments it declares, Lua's behavior, which Lota's own code carries and tests.

### Confirmation

- `test/callbacks_test.rb` checks that an undefined callback is skipped, that a callback receives only the arguments it declares, returns early, and can be wrapped by a prepended module that calls `super`.
- `test/boot_test.rb` and `test/settings_test.rb` check the folder, `conf.rb`, and its settings.
- `rake test:parity` runs the translated fixture games, which use these callbacks.
