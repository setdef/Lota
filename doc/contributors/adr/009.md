# ADR 009: A Game Is a Folder, with Callbacks as Methods on `Lota`

## Status

Accepted

## Date

2026-10-25

## Context and Problem

A LÖVE game is a folder with `main.lua` and an optional `conf.lua`. It defines callbacks as functions on the global `love` table (`function love.update(dt)`), and `love.run` calls those that exist. LÖVE code does more than define callbacks. Games call them (`love.draw()` to render into a canvas), check whether they exist (`if love.update then`), return from them early, and wrap them: game-state libraries save the current `love.update` and install one that calls it and then their own. How does a Lota game define its callbacks?

## Decision Drivers

- A LÖVE game translates line by line.
- Every way LÖVE code uses callbacks keeps working, including an early `return`.
- The result reads as Ruby.

## Considered Options

1. A folder with `conf.rb` and `main.rb`, whose callbacks are methods defined on the `Lota` module (`def Lota.update(dt)`).
2. Callbacks registered as blocks (`Lota.update { |dt| ... }`).

## Decision Outcome

Chosen: option 1. Ruby methods give every behavior LÖVE code relies on: call one (`Lota.draw`), check for one (`Lota.respond_to?(:update)`), return early, and wrap one by prepending a module to `Lota.singleton_class`. Option 2 fails on early returns: `return` inside a stored block raises `LocalJumpError` once the block outlives the code that defined it, and Lua games return early from callbacks routinely.

### Consequences

- Good, because a tutorial's `function love.x` and a Lota game's `def Lota.x` have the same shape, and a private `Kernel#lota` makes it `def lota.x`.
- Good, because a game-state library wraps callbacks with `prepend`, the Ruby way.
- Bad, because defining methods on another module's singleton is uncommon in Ruby code.
- Bad, because the core API has two spellings for the same modules, `Lota::Graphics` and `lota.graphics`, and `lota` is reserved everywhere, as `puts` is.
