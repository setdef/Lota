# ADR 010: Ship Games Through Fledge's Embedded Ruby

## Context and Problem Statement

A player of a fused LÖVE game double-clicks an app and it runs, with nothing to install. A Lota game needs a Ruby interpreter, the standard library, its gems, Lota's native extension, and LÖVE's engine, and almost no player has Ruby. How does a Lota game reach a player looking exactly like a fused LÖVE game?

## Decision Drivers

- The player installs nothing and sees an ordinary app.
- Ruby runs on the process's main thread, as the engine needs, with YJIT.
- The app controls its own layout and code signing on macOS.
- Nothing on the player's machine changes how the game runs.
- Upkeep of runtimes and launchers that one maintainer can carry.

## Considered Options

1. Fledge, the maintainer's packaging tool for Ruby apps, which embeds CRuby in a launcher and publishes a runtime for each platform.
2. A launcher and runtimes of Lota's own, built the same way.
3. A single-file packager such as Tebako or OCRAN.

## Decision Outcome

Chosen: option 1, so that Lota does not duplicate what Fledge already does.

Lota first chose option 2, on 2026-10-25, and a spike outside Lota's repository showed its core works on macOS: a small C launcher statically linking Ruby, running game code on the main thread with YJIT, and passing strict code-signature checks. Fledge grew from that design. Its founding architecture is the one Lota's decision of 2026-10-25 set out: a small C launcher that embeds CRuby, a prebuilt relocatable runtime for each platform, and rv-ruby and RubyInstaller as the sources of Ruby. When a second project, Tokra, needed the same, the maintainer had it built once as a shared tool for Lota, Tokra, Rooibos, and apps with no framework. Lota's launcher was only ever a spike outside Lota's repository, so Fledge is that design generalized and written afresh, which Lota then adopted, not code moved out of Lota. On 2026-11-02 two Lota games built with Fledge ran on macOS with no Ruby on the player's path, on the main thread, with YJIT, signed ad hoc and with the hardened runtime, and option 2 was dropped in its favour.

Option 3 lost on 2026-10-25: Tebako and OCRAN were built for command-line tools. They unpack to a temporary directory or mount a virtual filesystem on every launch, and they control less of a macOS app's layout and signing.

Confidence: high that a fused game runs as a player expects, medium that it ships. On every push, CI fuses three games on all five platforms and runs each app with no Ruby on its path. One of them draws Lövetest's screenshot scene and matches LÖVE's expected image pixel for pixel, as it also does on an RTX 4090 under Vulkan, and a sandboxed macOS app ran with YJIT on macOS 15 and 26. What no one has done yet is the last step to a player: no app has a Developer ID signature or notarization, so Apple's acceptance of the JIT's entitlements is unknown, and no person has installed the `.dmg` or the Windows installer.

### Consequences

- Good, because Lota writes a Fledge project and builds it with `lota fuse`, rather than maintaining a launcher and runtimes.
- Good, because Lota's gem needs nothing special: Fledge copies a game and the gems its lockfile names into its runtime.
- Good, because Lota's needs shape Fledge directly: the same maintainer sets both projects' priorities, so a fix Lota needs can land in Fledge first.
- Bad, because Lota's packaging depends on a second project's releases. `lota fuse` pins a Fledge version (`Lota::Fuse::FLEDGE_REF`), and each new Fledge release is a pin for the maintainer to move and test.
- Bad, because Lota publishes a precompiled gem per platform, matched to Fledge's Ruby, and a new Fledge Ruby needs a matching Lota gem first.
- Bad, because Fledge builds an app only on its own platform, so a developer builds on each platform they ship for, and CI fuses on five runners on every push.
- Bad, because a fused game is larger than a fused LÖVE game, about 93 MB unpacked on macOS.

### Confirmation

- `test/fuse_test.rb` checks what `lota fuse` writes and refuses.
- CI's `fuse` job runs `.github/workflows/fuse.yml`, which fuses `test/games/fuse`, `fuse_gems`, and `fuse_native` on every platform, runs each app with no Ruby on its path, and checks with `.github/fuse_check.rb` what it drew against LÖVE's expected image, and its saves, sound, notices, and restart. A release waits for every CI job to pass.
- `rake package:install` installs each precompiled gem into an empty `GEM_HOME` and runs a game from it.
