# ADR 011: Build for Windows with MinGW

## Status

Accepted

## Date

2026-11-02

## Context and Problem

Fledge's Windows runtime is RubyInstaller's Ruby, built with MinGW against the UCRT, for x64 and ARM64 (ADR 010). A native gem has to match the Ruby it loads into. LÖVE's own Windows builds use Microsoft's compiler. Which toolchain builds LÖVE's engine and Lota's extension on Windows?

## Decision Drivers

- The extension loads into RubyInstaller's Ruby.
- No change to LÖVE's source.
- The libraries match the versions LÖVE builds against.

## Considered Options

1. MinGW-UCRT, matching RubyInstaller's Ruby, with LÖVE's libraries built from source at LÖVE's versions.
2. Microsoft's compiler, as LÖVE's own builds use.
3. MinGW with MSYS2's packaged libraries.

## Decision Outcome

Chosen: option 1. A spike built LÖVE's engine and Lota's extension with MinGW-UCRT on x64 and ARM64 and loaded Lota in RubyInstaller's Ruby, with no change to LÖVE's source. Option 2 would not match the only Ruby Fledge ships on Windows. Option 3's libraries are newer than LÖVE's, and building from source keeps OpenAL Soft the only LGPL library in a game.

### Consequences

- Good, because Lota's gems load in the same Ruby Fledge ships.
- Bad, because Lota's Windows build differs from LÖVE's, so a parity test on Windows also has to run against LÖVE's own build of the same commit.
- Bad, because the gem carries the compiler's runtime (libstdc++ or libc++, and winpthreads) linked in.
