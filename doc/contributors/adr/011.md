# ADR 011: Build for Windows with MinGW

## Context and Problem Statement

Fledge's Windows runtime is RubyInstaller's Ruby, built with MinGW against the UCRT, for x64 and ARM64 ([ADR 010](010.md)). A native gem has to match the Ruby it loads into. LÖVE's own Windows builds use Microsoft's compiler. Which toolchain builds LÖVE's engine and Lota's extension on Windows?

## Decision Drivers

- The extension loads into RubyInstaller's Ruby.
- No change to LÖVE's source.
- The libraries match the versions LÖVE builds against.
- No LGPL library in a game but OpenAL Soft.

## Considered Options

1. MinGW-UCRT, matching RubyInstaller's Ruby, with LÖVE's libraries built from source at LÖVE's versions.
2. Microsoft's compiler, as LÖVE's own builds use.
3. MinGW with MSYS2's packaged libraries.

## Decision Outcome

Chosen: option 1, because a native gem has to match the Ruby it loads into, and Fledge's only Windows Ruby is RubyInstaller's, built with MinGW. A spike on 2026-11-02 built LÖVE's engine and Lota's extension that way, for x64 and ARM64, and loaded them with no change to LÖVE's source. That is why option 2 lost: it needs a Ruby built with Microsoft's compiler, which Lota or Fledge would have to build and maintain. It becomes viable if Fledge ships one. Option 3 lost because MSYS2's libraries are newer than the versions LÖVE builds against, and building from source keeps OpenAL Soft the only LGPL library in a game.

Confidence: high for x64, medium for ARM64. CI builds both gems, installs each on a runner without MSYS2, and runs Lota's tests on Mesa's llvmpipe, and a game built on this toolchain has been played on a Windows PC, with its window, input, and sound. On an NVIDIA RTX 4090, Lövetest gives the same results, on both Vulkan and OpenGL, in Lota's x64 build and in LÖVE's own build of the same commit: the same passes and the same 13 skips, and LÖVE's `setGrabbed` test fails only where its window lacks keyboard focus, as Lota's would. At a 300% display scale both report the same window size and DPI scale. The ARM64 build has run only on CI.

### Consequences

- Good, because Lota's gems load in the same Ruby Fledge ships.
- Bad, because Lota's Windows build differs from LÖVE's, so a difference seen on Windows has to be checked against LÖVE's own build of the same commit, by hand, as the comparison of 2026-11-09 was; the parity harness runs only on macOS and Linux.
- Bad, because two toolchains build the gems, GCC for x64 and clang for ARM64, and CI builds every library LÖVE links from source for both.
- Bad, because the gem carries the compiler's runtime linked in (libstdc++ or libc++, and winpthreads), whose notices the maintainer decides how to credit.
- Bad, because Ruby's MinGW import library exports some of Windows' own functions, such as `Sleep`, under Ruby's DLL, so each extension links kernel32 first, and the gem's DLL check refuses a binary that takes a kernel32 function from Ruby.

### Confirmation

- CI's `windows-build` job builds both architectures with `tasks/windows_build.rb`, checks which DLLs the extension loads and from where, and opens a window with OpenGL on each.
- CI's `windows-delivery` job installs each gem on a runner without MSYS2 and plays a sound through the gem's `OpenAL32.dll`. A release waits for both.
- The gem build refuses a binary that imports a DLL that is neither the gem's, Ruby's, nor one of Windows' own (`NativeFormat::PE`, tested by `test/tasks/native_format_pe_test.rb`).
