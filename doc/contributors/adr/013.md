# ADR 013: Require Ruby 4.1 from Its Previews, and Ship 1.0 Only on Ruby 4.1.0

## Context and Problem Statement

Lota requires Ruby 4.0.1 or newer (`lota.gemspec`), and each precompiled gem accepts only the Ruby minor it was built for (`tasks/native_gem.rb`, `required_ruby_version`). Ruby 4.1 is due around Christmas 2026; its first preview, `v4.1.0-preview1`, was tagged on 2026-10-11. Ruby does not follow SemVer, so a minor release can break what ran on the one before. Players never meet that Ruby: `lota fuse` ships a Ruby inside each game's app, through Fledge ([ADR 010](010.md)). Developers do meet it, since `lota run` and `lota fuse` use the developer's own Ruby. Lota has no users outside setdef yet, and its 1.0.0 will freeze its API. Which Ruby does Lota build on now, and which does 1.0 ship on?

## Decision Drivers

- A player installs nothing, Ruby included, whatever Ruby Lota requires.
- Lota's `love.thread` cannot run safely on Ruby 4.0 (below).
- No work done now only to be undone at 1.0.
- One maintainer builds, tests, and publishes a gem per platform for each Ruby minor Lota supports.
- Lota ships through Fledge, so Lota can require a Ruby only once Fledge publishes runtimes for it.

## Considered Options

1. Require Ruby 4.1 from its first previews, drop 4.0 now, and ship 1.0.0 only once Ruby 4.1.0 is released.
2. Require Ruby 4.1 from its release, staying on 4.0 until then.
3. Keep supporting Ruby 4.0.
4. Support 4.0 and 4.1 side by side for a while.

All four were weighed on 2026-11-09, after a spike ran Lota on 4.1.0-preview1 on every platform it supports.

## Decision Outcome

Chosen: option 1. `lota fuse` ships Ruby inside each game's app, so requiring the newest Ruby costs a player nothing; Lota has no outside users to strand; and staying on 4.0 until 1.0 would mean work that 1.0 then undoes. Lota and Fledge move together, and neither ships 1.0.0 before Ruby 4.1.0 is released. Fledge's own reason for the same choice is its 1.0 contract, which keeps every Ruby minor its 1.0 has a runtime for until its next major.

Option 2 lost because Lota would stay on 4.0 for weeks, with threads waiting on a branch and the spike's fixes waiting with them, only to move at 1.0 anyway. Option 3 lost because Lota's `love.thread` waits as long as Lota supports 4.0. Option 4 lost on its cost: two sets of platform gems in CI and every release, with threads working in only one.

Lota's move lands on trunk together with Fledge's first release built on Ruby 4.1, because once Lota's gems require 4.1, `lota fuse`, the phone builds, and CI's fuse checks need Fledge's 4.1 runtimes.

What 4.1 changes for Lota, from its `NEWS.md` on Ruby's master branch at `0e25874` (2026-11-09) and from bugs.ruby-lang.org:

- `rb_gc_register_address` registers an address with the calling Ractor, and only that Ractor's collector marks it (Feature #22277, commit `2ad6b99a98`, in 4.1.0-preview1). On 4.0 every Ractor shares one list, changed with no lock (`gc.c` at `v4.0.7`, lines 3443-3487), and Rice registers every object it holds there, so two Ractors calling Lota at once corrupt it.
- Each Ractor's heap is collected on its own thread, without stopping the others.
- A class or module can be changed only by the Ractor that made it, and everything `require`d belongs to the main Ractor (Feature #22226). `Ractor.new`'s block may read outer locals that are never reassigned (Feature #22444). `receive` and `select` take `timeout:` (Feature #22255), `Ractor#alive?` is new (Feature #22441), and `Ractor#value` answers once.
- `RUBY_MN_THREADS=2` puts the main thread on the M:N scheduler, where it is no longer bound to the process's first thread. The engine needs that thread, so Lota's main-thread rule ([ADR 007](007.md)) fails under it; the default leaves the main thread 1:1, and a game Fledge builds never sees the variable while Ruby starts.
- ZJIT inlines small methods, blocks included. YJIT gains Windows, but only for mswin; RubyInstaller's MinGW Ruby gets none.
- 4.1 does not free a dropped `Ruby::Box` that defined a class, which [ADR 012](012.md)'s in-process restart waits for. On 4.1.0-preview1 (`2d08b5f42f`), five dropped boxes that each defined a class were all still alive after full collections, as on 4.0.7, though five empty boxes were freed. NEWS lists no change to boxes, and Bug #22403 is open with no target version.

Confidence: high that Lota runs on 4.1, from previews. On Ruby 4.1.0-preview1 (RubyInstaller's head build on Windows), Lota's suite passed on macOS arm64, Linux x86_64 and arm64, and Windows x64 and ARM64. Its phone check ran on an Android phone and in the iOS Simulator and started on an iPhone, all with Fledge's 4.1 runtimes, and a fused app ran on Linux. Its Ractor work passed with no workaround of its own. That took only small fixes: version pins, Bundler's later setup, the `ruby_abi_version` symbol a preview Ruby demands of an extension, and a new field of `rb_data_type_t`. Left before Lota moves: a false warning from RubyGems 4.1, two DLLs RubyInstaller's head build leaves out, and Fledge's first 4.1 release.

### Consequences

- Good, because `love.thread`'s Ractors run on Ruby's own `rb_gc_register_address`, with no workaround of Lota's to keep and later remove.
- Good, because Lota builds, tests, and publishes one Ruby minor's gems, not two, and 1.0 starts on the Ruby it will live on.
- Good, because a 4.1 problem found now has weeks to be fixed before 1.0.
- Bad, because a developer needs a Ruby 4.1 preview to run `lota run` or `lota fuse`, and Lota versions after the move refuse 4.0.
- Bad, because each preview, the release candidate, and 4.1.0 need every platform gem rebuilt, about three rounds, and a bug in a preview can stop Lota's trunk until it is fixed or worked around.
- Bad, because Windows has no numbered preview, so its Ruby is a pinned snapshot of RubyInstaller's rolling head build, which Fledge keeps a copy of and which lacks two DLLs Fledge's runtime adds.
- Bad, because Lota 1.0.0 waits for Ruby 4.1.0 and for Fledge's runtimes built on it, which RubyInstaller's history puts in early January.
- Bad, because 4.1's Ractors bind Lota's threads more tightly (class ownership, `Ractor.new`'s isolation, `#value` once), and each preview may change them again, so the Ractor work is rerun on every preview.

### Confirmation

- `lota.gemspec`'s `required_ruby_version` becomes `>= 4.1.0.a`, which RubyGems reads as accepting 4.1's previews and refusing 4.0.
- Each precompiled gem takes the source gem's floor and stops below 4.2 (`tasks/native_gem.rb`), which `test/tasks/native_gem_test.rb` checks.
- CI runs on the Ruby `mise.toml` pins, and on no 4.0; `lota fuse` pins a Fledge release built on 4.1 (`Lota::Fuse::FLEDGE_REF`).
- The release procedure refuses to tag 1.0.0 while the pinned Ruby is a preview.
