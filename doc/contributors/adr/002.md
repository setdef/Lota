# ADR 002: Ship a Lota Game as LÖVE Ships a Fused Game

## Status
Accepted. Amended 2026-11-02: Fledge builds the runtime and the app, and sections 1 to 5 changed with that.

## Date
2026-10-25

## Context

A player who downloads a game made with LÖVE never meets LÖVE or Lua. The developer "fuses" the game: they join the zipped game onto LÖVE's executable (a renamed `.exe` beside its DLLs on Windows, a renamed `.app` with the game inside on macOS, an AppImage on Linux), and at boot LÖVE notices that its own executable carries a game and runs it (`vendor/love/src/modules/love/boot.lua`, lines 76–96). The player double-clicks an app, and it runs.

A Lota game needs more than a LÖVE game does: a Ruby interpreter, Ruby's standard library, the game's gems, Lota's native extension, and LÖVE's engine with its libraries. Almost no player has Ruby installed. A player of a Lota game must still see exactly what a player of a fused LÖVE game sees.

A spike (`rove_2d-spikes/spike5`, outside the repository) proved the core of it on macOS: a 35-line C launcher that statically links a prebuilt Ruby 4.0.9, finds its standard library inside its own app bundle, runs game code on the main thread with YJIT on, loads Lota's extension unchanged, and passes strict code-signature verification.

Fledge (github.com/setdef/Fledge), the maintainer's packaging tool for Ruby apps, does that work for every Ruby app. A second spike on 2026-11-02 built Lota's arm64-darwin platform gem and put two games through `fledge build` (tag v0.0.1.pre.17). Both built on the first try. The app ran with no Ruby on the player's path, on the process's main thread, with YJIT on, drew, played audio, loaded SDL3 and the other frameworks from inside the app, and passed `codesign --verify --deep --strict`, ad hoc and with the hardened runtime. Lota has no reason to build a launcher and a runtime of its own beside it.

## Decision

### 1. Fledge's launcher embeds Ruby, as LÖVE's executable embeds Lua

Fledge's launcher is a small C program modeled on Ruby's own `main.c`. It embeds CRuby, sets the player's own Ruby environment aside so nothing on the player's machine changes the game, and runs Ruby on the process's main thread, as ADR 001 section 6 asks. Lota's entry script enables YJIT where the runtime has it. Fledge's launcher does not.

Single-file packagers such as Tebako and OCRAN were built for command-line tools: they unpack to a temporary directory or mount a virtual filesystem on every launch, and they control less of a macOS app's layout and signing than a launcher does.

### 2. Fledge publishes the runtimes, and Lota publishes a gem for each platform

Fledge builds a runtime for each platform: Ruby with its whole standard library and default gems, and the launcher. Lota publishes its native extension as a precompiled gem for each platform, with LÖVE's engine libraries beside it. A game's Gemfile asks for `lota`, and Fledge copies the game and the gems its lockfile names into the runtime.

Fledge builds an app on a computer of the app's own platform, and a native gem has to match the Ruby it loads into. A developer builds each platform's app on that platform, or on a continuous integration runner for it. One machine does not build for every platform.

The standard library ships whole, as LÖVE ships the whole of Lua's, because a game that requires a library and finds it missing is broken. Bundled gems are gems like any other: a runtime carries one only when the game's Gemfile asks for it.

Intel Macs and musl Linux wait. Fledge builds no Intel Mac runtime, and few players of a game run Alpine. Phones wait for Fledge to link native extensions into its mobile runtimes, which it does not yet do; before then they run pure Ruby. Neither the Lota gem nor `lota fuse` targets them until it does.

### 3. Ruby comes from Fledge's runtimes

Fledge chooses where each platform's Ruby comes from (`runtime/sources.yml` in its repository), and Lota's gem names the Ruby versions it was built for, so a new Fledge Ruby needs a matching Lota gem first. The first spike used rv-ruby, which publishes prebuilt, relocatable Ruby 4.0 builds for macOS and Linux with a static libruby, YJIT, and ZJIT, and Apple Silicon needs macOS 14 or newer there. Lota supports macOS 15 and newer.

### 4. Windows uses MinGW

Fledge's Windows runtime is RubyInstaller's Ruby, built with MinGW against the UCRT, for x64 and ARM64. A native gem has to match, so Lota builds LÖVE's engine and its libraries with MinGW, which LÖVE's own builds do not do. A spike on 2026-11-02 showed that LÖVE's engine and Lota's extension compile and load that way with no change to LÖVE's source. Lota builds the libraries from source at the versions LÖVE builds against (ADR 001, section 1), not from MSYS2's newer packages, which keeps OpenAL Soft the only LGPL library in a game.

### 5. Developers run `lota run` and `lota fuse`

During development, `lota run` runs a game on the developer's own Ruby, as `love path/to/game` does, following `rooibos run`. For release, `lota fuse` turns a game folder into a Fledge project and builds it:

- It reads `conf.rb` for the game's name and `t.identity`.
- It writes a Gemfile that pins `lota` to the running version and Fledge to a release tag. Fledge is not on RubyGems.org, so the Gemfile names it by Git tag, and `lota fuse` needs the network and Git.
- It writes an entry script that boots the game as a fused game (`Lota::Boot.new(game_dir, ARGV, fused: true)`) and turns YJIT on where the runtime has it.
- It writes `fledge.yml`, and copies the game into a folder named for its identity. The game's `t.version` names the version of LÖVE it was written for, so it never becomes the app's version.
- It runs `fledge build`, passes `--sign` along, and prints the paths Fledge reports.
- It says that this built the app for this computer's platform only.

A fused game saves where LÖVE's fused game saves (ADR 003, section 8). Fledge puts the game in a folder called `app`, so the folder named for the identity keeps a game without `t.identity` from saving to `app`.

## Consequences

- Lota's continuous integration builds and publishes a platform gem for every supported platform, so precompiled gems are part of the product, not an optimization. Fledge builds and publishes the runtimes.
- An app developer using Lota builds on each platform they ship for. Lota's own gems build on a runner for each.
- A fused game carries a Ruby interpreter, the standard library, and LÖVE's engine, so it is larger than a fused LÖVE game: about 93 MB unpacked on macOS in the second spike.
- The macOS app is code-signed with the hardened runtime. Ruby's JITs mark memory executable with plain `mprotect` rather than `MAP_JIT`, so Fledge's signature carries `com.apple.security.cs.allow-unsigned-executable-memory` and `com.apple.security.cs.disable-library-validation`. LÖVE's own macOS build already declares the first (`vendor/love/platform/xcode/love.entitlements`). YJIT ran under both, signed ad hoc. Whether notarization accepts them under a Developer ID signature is confirmed when Lota first signs one.
- OpenAL Soft is LGPL, so it ships as a separate framework a player can replace, with its source archive inside the app. FreeType's license asks for a credit in a product's documentation, so `lota fuse` adds one to the notices it writes.
- A fused game ships Lota itself, and with it Lota's license. Lota and Fledge are both AGPL-3.0-or-later, so a developer who distributes a game offers the Corresponding Source for both.
