# ADR 004: Run LÖVE's Own C++ Engine and Replace Only Its Lua

## Context and Problem Statement

Lota lets Rubyists make 2D games the way LÖVE lets Lua programmers make them. LÖVE is a C++ engine that hands control to Lua: `boot.lua` starts the game, `callbacks.lua` runs its loop, and 156 `wrap_*.cpp` files expose the engine to Lua. A decade of tutorials teaches games in that API.

A game written in Lota has to behave as the same game written in LÖVE: the same physics, rendering, audio, and event order. A platformer ported line for line has to jump, slide, and collide the same way, or the tutorials stop being true. Where does that behavior come from?

## Decision Drivers

- Same behavior as LÖVE, down to physics contacts and event order.
- Parity that a test checks against LÖVE itself, not a claim.
- Ruby owns the game loop, in place of Lua.
- Upkeep across LÖVE's releases that one maintainer can carry.

## Considered Options

1. Bind LÖVE's own C++ engine, and replace only the Lua around it.
2. Build an engine of Lota's own from other libraries, as Ruby 2D builds on SDL.
3. Build LÖVE's API on an existing Ruby game library: Gosu, or raylib's Ruby bindings.
4. Run LÖVE whole, Lua included, and drive it from Ruby through a Lua bridge.

Options 1 and 2 were weighed before the decision of 2026-10-24. Options 3 and 4 were researched on 2026-11-09, after it.

## Decision Outcome

Chosen: option 1, because only LÖVE's own engine gives a game LÖVE's behavior. In a game, behavior is the product, and LÖVE's renderer, audio, physics, shader dialect, and batching are that behavior. Lota compiles the engine at a pinned commit without its Lua layer, ports `boot.lua` and `callbacks.lua` to Ruby line by line, and binds the rest.

Option 2 lost for that reason: an engine built from other libraries could imitate LÖVE's behavior but not share it. The reason was stated for any engine but LÖVE's, so it covers option 3 too, though neither Gosu nor raylib was named at the time. Option 4 runs LÖVE's own engine, so the reason does not apply to it. Option 4 was never weighed, and no reason for choosing option 1 over it was recorded. What the later research found is in "Pros and Cons of the Options".

Confidence: high that option 1 works. A spike linked the engine with no Lua symbols and drew through it. The reference `love` built from the same commit passes Lövetest, 349 of 349 tests on Metal. The parity harness ran KleleAtoms in both engines: all 399 frames match, its sounds match sample for sample, and its saves byte for byte. Upkeep has the weakest evidence: no LÖVE upgrade has gone through the process yet. Whether option 1 is better than option 4 is unknown.

### Consequences

- Good, because parity is testable. Both engines run the same C++, so the same game in Lua and in Ruby runs side by side on the pinned commit and is compared frame by frame.
- Good, because LÖVE's documentation, wiki, and tutorials describe Lota's behavior too.
- Bad, because building Lota means building LÖVE. A contributor installs LÖVE's dependencies, and a clean build compiles a large C++ codebase: 49 seconds on a 10-core M1 Max. CI compiles it for every platform Lota ships, on every push. Players and game developers install precompiled gems and compile nothing.
- Bad, because each upgrade of LÖVE is the maintainer's work: bump the submodule, regenerate the source lists and bindings, port the patches, and rerun the parity tests.
- Bad, because LÖVE's defects become Lota's. Lota works around a defect in its own code, or patches as a last resort ([ADR 005](005.md)).

### Confirmation

- `rake test:parity` runs each fixture game in a reference `love` built from `vendor/love` and in Lota, and compares them frame by frame.
- Lövetest's tests, translated in `test/lovetest`, pass in Lota.
- `rake engine:sources:check` fails when the engine's source lists differ from what the pinned commit generates.

The gate (`bundle exec rake`) and CI run all three.

## Pros and Cons of the Options

The facts about Ruby 2D, Gosu, raylib, and rufus-lua below come from the research of 2026-11-09.

### Build an engine of Lota's own from other libraries

Ruby 2D 1.0.0 (2026-08-07, MIT) draws through a C extension of its own over SDL3, SDL3_image, SDL3_mixer, and SDL3_ttf.

- Good, because the native layer stays small, and Lota would own all of it.
- Bad, because LÖVE's renderer, Box2D integration, shader dialect, and audio would be rewritten. Parity could only be imitated, never shared, and each difference found would be Lota's to fix.

### Build on Gosu or raylib's Ruby bindings

Gosu is a C++ library for Ruby and C++, built on SDL2; its newest gem is 2.0.0.pre8, from 2024-02-25. raylib-bindings binds raylib 6.1-dev through the ffi gem and ships prebuilt libraries; its newest release is 0.8.4, from 2026-09-05.

- Good, because a maintained binding and prebuilt libraries already exist, for raylib.
- Bad, because neither is LÖVE's engine. LÖVE's API would be emulated over another renderer, audio system, and physics engine (raylib's bindings carry Physac, not Box2D), so behavior would differ wherever the engines do.

### Run LÖVE whole and drive it through a Lua bridge

LÖVE runs unchanged, and Ruby talks to its Lua state. The Ruby gem for embedding Lua, rufus-lua, does it through the ffi gem.

- Good, because LÖVE's engine and behavior stay whole, and so does its wrap layer, with its arities and error messages. Lota would write no patch and no binding generator.
- Bad, because `love.run` stays in Lua. Lua owns the loop, and every callback crosses from Lua into Ruby, every frame.
- Bad, because each engine object lives under two garbage collectors, Lua's and Ruby's.
- Bad, because rufus-lua was archived on 2024-03-09, works with Lua 5.1 alone, and does not load LuaJIT, which LÖVE's own Lua code targets, without changes. Lota would maintain a bridge as well as a binding.
