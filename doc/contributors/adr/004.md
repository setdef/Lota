# ADR 004: Run LÖVE's Own C++ Engine and Replace Only Its Lua

## Context and Problem Statement

Lota lets Rubyists make 2D games the way LÖVE lets Lua programmers make them. LÖVE is a C++ engine that hands control to Lua, and a decade of tutorials teaches games in its API. A game written in Lota has to behave as the same game written in LÖVE: the same physics, rendering, audio, and event order, or the tutorials stop being true. Where does that behavior come from?

## Decision Drivers

- Same behavior as LÖVE, down to physics contacts and event order.
- Parity that a test checks against LÖVE itself, not a claim.
- Ruby owns the game loop, in place of Lua.
- Upkeep across LÖVE's releases that one maintainer can carry.

## Considered Options

1. Bind LÖVE's own C++ engine, and replace only the Lua around it.
2. Build an engine of Lota's own from other libraries, as Ruby 2D builds on SDL.
3. Build LÖVE's API on an existing Ruby game library: Gosu, or raylib's Ruby bindings.
4. Run LÖVE whole, Lua included, and drive it from Ruby through a Lua bridge.

Options 1 and 2 were weighed before the decision. Options 3 and 4 were researched on 2026-11-09, after it.

## Decision Outcome

Chosen: option 1, because only LÖVE's own engine gives a game LÖVE's behavior. In a game, behavior is the product, and LÖVE's renderer, audio, physics, shader dialect, and batching are that behavior. Lota compiles the engine at a pinned commit without its Lua layer, ports LÖVE's Lua boot sequence and loop to Ruby, and binds the rest.

Option 2 lost for that reason: an engine built from other libraries could imitate LÖVE's behavior but not share it. The reason covers option 3 too, though neither Gosu nor raylib was named at the time; the later research found that option 3 would emulate LÖVE's API over another renderer, audio system, and physics engine. Option 4 runs LÖVE's own engine, so the reason does not apply to it. It was never weighed, and no reason for preferring option 1 was recorded. The later research found that it keeps LÖVE's wrap layer whole and needs no patches or binding generator, but leaves the loop in Lua, so every callback crosses from Lua into Ruby every frame, puts each engine object under two garbage collectors, and rests on rufus-lua, the Ruby gem for embedding Lua, which was archived on 2024-03-09.

Confidence: high that option 1 works, since published LÖVE games run in Lota and in LÖVE and match frame by frame; low for upkeep, since no upgrade of LÖVE has been done yet; unknown whether option 1 is better than option 4.

### Consequences

- Good, because parity is testable: both engines run the same C++, so the same game in Lua and in Ruby runs side by side and is compared frame by frame.
- Good, because LÖVE's documentation, wiki, and tutorials describe Lota's behavior too.
- Bad, because building Lota means building LÖVE. A contributor installs LÖVE's dependencies and compiles a large C++ codebase, and CI compiles it for every platform on every push. Players and game developers install precompiled gems.
- Bad, because each upgrade of LÖVE is the maintainer's work: bump the submodule, regenerate the source lists and bindings, port the patches, and rerun the parity tests.
- Bad, because LÖVE's defects become Lota's. Lota works around a defect in its own code, or patches as a last resort ([design/engine.md](../design/engine.md), "Patch files").

### Confirmation

The parity harness and Lövetest's tests, translated, run in the gate and in CI against the pinned commit.
