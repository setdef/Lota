# ADR 006: Bind the Engine with Rice

## Status

Accepted

## Date

2026-10-24, kept after measurement on 2026-10-26 and 2026-10-28

## Context and Problem

Ruby has to call LÖVE's C++ classes and receive their objects. LÖVE's `wrap_*.cpp` files record each function's arity, overloads, defaults, and error messages for Lua, and each binding has to reproduce them. How does Lota bind C++ to Ruby?

## Decision Drivers

- No third language between Ruby and LÖVE.
- Bindings a generator can write from the `wrap_*.cpp` files.
- Engine objects that Ractors can share where LÖVE allows it.
- A call cheap enough for a game's frame.

## Considered Options

1. Rice, which binds C++ classes to Ruby directly.
2. Ruby's C API, written directly, which the generator could emit.
3. Thin Rice bindings of the engine's methods, with the wrap logic in Ruby.

## Decision Outcome

Chosen: option 1, Rice 4.12.0. It binds C++ classes with no third language, and the generator writes its bindings.

Option 2 costs a few nanoseconds a call against Rice's 0.4 to 0.85 µs, but the fixture games spend under 1% of a frame on binding calls, and the heaviest 7 to 13%. Lota revisits it when a fixture game's binding cost becomes a problem. Option 3 would remove only about 40 to 55% of the C++, would cost nothing per call only if every binding were written with care, and would make Rice's enum values unshareable between Ractors.

### Consequences

- Good, because bindings are plain C++ that a generator writes from LÖVE's own wrap files.
- Good, because Rice handles conversions, ownership, and exceptions in one place.
- Bad, because a call costs about ten times what LÖVE's does, mostly Rice rebuilding its argument map on every call: 10,000 draws a frame take about 8 ms in Lota against 0.5 ms in LÖVE.
- Bad, because Lota depends on Rice's releases, and on its source for what it does.
