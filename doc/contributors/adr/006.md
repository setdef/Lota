# ADR 006: Bind the Engine with Rice, and Revisit Ruby's C API When a Game's Binding Cost Calls for It

## Context and Problem Statement

Ruby has to call LÖVE's C++ classes and receive their objects. LÖVE's `wrap_*.cpp` files record each function's arity, overloads, defaults, and error messages for Lua, and each binding reproduces them. LÖVE has about 1,100 functions and methods, so a generator writes most bindings. How does Lota bind C++ to Ruby?

## Decision Drivers

- No third language between Ruby and LÖVE.
- Bindings a generator writes from the `wrap_*.cpp` files.
- Engine objects that Ractors can share where LÖVE allows it.
- A call cheap enough for a game's frame, on every platform Lota ships, phones included.

## Considered Options

1. Rice, which binds C++ classes to Ruby.
2. Ruby's C API, written directly, which the generator could emit.
3. Thin Rice bindings of the engine's methods, with the wrap logic in Ruby.
4. Rust, through Magnus and cxx.
5. Ruby's FFI, through the ffi gem or Fiddle, over a C layer of Lota's own.
6. SWIG, which generates wrappers from C++ headers and interface files.

Options 1 to 4 were weighed between 2026-10-24 and 2026-10-28, options 2 and 3 with measurements. Options 5 and 6 were researched on 2026-11-09, after the decision.

## Decision Outcome

Chosen: option 1, Rice 4.12.0, because it binds C++ classes with no third language between Ruby and LÖVE, and because the games measured did not need the speed of option 2.

Option 4 lost on 2026-10-24: going from Ruby through Magnus and cxx to C++ adds two layers and a second build system. The maintainer deferred to that advice.

Option 2 lost because its speed did not matter yet, not on its merits. A spike on 2026-10-24 measured a Rice call at 60 to 330 ns, against about 6 ns through Ruby's C API. On 2026-10-26 `rake bench` showed 10,000 draws a frame take about 8 ms in Lota against 0.5 ms in LÖVE. The maintainer kept Rice because that load is a benchmark's, not a game's: the fixture games spend under 1% of a frame on binding calls, and the heaviest, flash-blip, 7 to 13%. The record names one cost of option 2: Lota would take on what Rice handles, the hardest part being C++ exceptions turned into Ruby exceptions. Patching Rice's slow path was offered at the same time, and no reason for passing it over was recorded. Lota revisits option 2 when a game's binding cost calls for it: when flash-blip runs in Lota, and when phones, which run Ruby without a JIT, are measured.

The phones were measured on 2026-11-09, and Rice stays. An iPhone 12 mini running iOS 27, a near-worst case for iOS, pays about 1.35 µs a draw, so flash-blip would fit in a frame there. A OnePlus Nord N30, a mid-range Android phone, pays about 4 µs a draw, where LÖVE pays 0.18 µs on the same phone, so flash-blip's 1,300 to 2,600 calls a frame could take a third of a frame or nearly all of it. When flash-blip runs in Lota, Lota measures it on that kind of phone and weighs the options again; keeping Rice is one of them.

Option 3 lost on 2026-10-28, measured against the maintainer's condition for it: that it remove most of the C++ and cost almost nothing per call. It would remove only about 40 to 55% of the C++, would cost nothing per call only if every binding were written with care, and would make Rice's enum values unshareable between Ractors.

Options 5 and 6 were never weighed against Rice. What the later research found is in "Pros and Cons of the Options".

Confidence: medium that Rice is fast enough. `rake bench` measured Rice's cost per call and each fixture game's share of a frame on desktops, and its workload ran on both phones above. flash-blip does not run in Lota yet, so the heaviest load is still an estimate, and on a mid-range Android phone that estimate is close to a whole frame. Rice is not known to be better than options 2, 5, or 6.

### Consequences

- Good, because bindings are plain C++ that a generator writes from LÖVE's own wrap files, and `ext/lota/bindings.rb` records why each of the rest is written by hand.
- Good, because Rice translates LÖVE's C++ exceptions into Ruby exceptions in one place, so no binding handles them by hand.
- Bad, because a call costs about ten times what LÖVE's does, mostly Rice rebuilding its argument map on every call: 10,000 draws a frame take about 8 ms in Lota against 0.5 ms in LÖVE.
- Bad, because a phone multiplies that cost. A mid-range Android phone pays about five times a desktop's per call and twenty times LÖVE's on the same phone. The missing JIT is not the cause, since YJIT saves only 2 to 15% of a call on a desktop; about a fifth of the phone's cost is allocating and freeing memory.
- Bad, because Lota depends on Rice's releases and reads its source for what it does. Rice's `bin/rice-rbs.rb` writes invalid, incomplete signatures, so Lota's generator writes the RBS itself. MinGW's GCC warns inside Rice's and Ruby's headers, so `binding.hpp` turns `-Warray-bounds` off for those headers alone.
- Bad, because the extension compiles against Ruby's headers, so each gem names the Ruby versions it was built for, and a new Ruby needs a new build on each platform.
- Bad, because a move to Ruby's C API, if it comes, means a second code path in the generator for the maintainer to keep, beside Rice's.

### Confirmation

- `rake bindings:check` fails when the generated bindings differ from what the generator writes.
- `rake bench` measures the cost of a call in Lota and in LÖVE, and `test/parity/bench_games_test.rb` keeps both benchmark games running in the gate.
- `test/native/memory_test.rb`, run under AddressSanitizer by `rake test:native`, checks that a wrapper retains and releases its engine object.

## Pros and Cons of the Options

### Ruby's FFI, through the ffi gem or Fiddle

FFI calls C functions through libffi. LÖVE's API is C++ classes, so Lota would first write a C function for each method.

- Good, because the native library does not compile against Ruby's headers, so one build serves every Ruby version, where a Rice extension is rebuilt for each.
- Bad, because that C layer is a binding of its own, generated or written beside the FFI declarations: two layers where Rice has one.
- Bad, because every call goes through libffi's generic call path.
- Bad, because Fledge's iOS runtime leaves Fiddle out for App Store review, and iOS offers no libffi to build it against.

### SWIG

SWIG generates Ruby wrappers for C++ classes from headers and interface files, handling most overloads and mapping exceptions through `%exception`.

- Good, because a mature tool writes the wrappers.
- Bad, because SWIG's interface files are a third language between Ruby and LÖVE.
- Bad, because LÖVE's arities, defaults, and error messages live in the `wrap_*.cpp` files, not in the headers SWIG reads, so each function would still need an interface entry or typemap of its own.
