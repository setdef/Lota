# ADR 016: Play a Game from One `.lota` File by Unpacking It

## Context and Problem Statement

A LÖVE game can be handed out as one file: its folder, zipped and renamed `.love`. A player who has installed LÖVE's own app, the engine with no game in it, plays one by opening it or by dropping it on the app's "no game" screen ([`boot.lua`, lines 52–60](https://github.com/love2d/love/blob/b7daef0f7c1dc5888090f5d5b22d4eaf4ffd1d87/src/modules/love/boot.lua#L52-L60)). A developer runs one with `love game.love`. LÖVE's team publishes that app for desktops and, with each release, for Android ([love-android's README](https://github.com/love2d/love-android/blob/main/README.md)), but not for iOS.

Lota's engine already reads a game's assets from a zip, through LÖVE's [PhysFS](https://icculus.org/physfs/). Ruby, though, loads code only from real files, and Fledge, which builds Lota's apps ([ADR 010](010.md)), runs no program through a virtual filesystem ([Fledge's ADR 032](https://github.com/setdef/Fledge/blob/trunk/doc/contributors/adr/032.md)). How does a Lota game play from one file?

## Decision Drivers

- A game is handed out and played as a LÖVE game is ([AGENTS.md](../../../AGENTS.md), "Design precedence").
- A newcomer who has never used a terminal shares a game by zipping its folder.
- The game's Ruby behaves as it does from its folder: `require`, `require_relative`, `__dir__`, `File`, and its error messages.

## Considered Options

1. Unpack the archive to a cache folder, and run the game from there.
2. Read the game's Ruby from inside the zip, through a hook on `require`.
3. Play no archive; accept one only as input to a tool that makes an app of it.
4. No single-file games.

All four were weighed on 2026-11-13, after a throwaway spike ran a game from an archive in Lota through options 1 and 2.

## Decision Outcome

Chosen: option 1, because it alone plays a game from one file as LÖVE does while the game's Ruby sees real files. The maintainer decided on 2026-11-13.

Lota ships a player app, built with Fledge, for desktops and Android, and none for iOS, as LÖVE ships none. It plays a `.lota` that is opened with it or dropped on its "no game" screen, and adds nothing to what LÖVE's app does. `lota run game.lota` plays one too. A `.lota` holds a game's Ruby files and assets, and its code may `require` Lota, Ruby's standard library, and the gems the player app ships. It holds no native code, as LÖVE cannot load a native module from a `.love` either ([`wrap_Filesystem.cpp`, line 1011](https://github.com/love2d/love/blob/b7daef0f7c1dc5888090f5d5b22d4eaf4ffd1d87/src/modules/filesystem/wrap_Filesystem.cpp#L1011)). The player unpacks the whole archive, so `File` reads the game's assets too. LÖVE's `io.open` cannot read a `.love`'s files, but LÖVE promises no such failure, so this adds to LÖVE rather than departing from it.

The extension is `.lota`, not `.love`, because a Lota archive holds Ruby, which LÖVE's app cannot run, and an app Fledge builds is offered for a file type without becoming its default, so a shared extension would open LÖVE's app.

Option 2 lost because the spike showed what it breaks: `require_relative` has to be rewritten whole, `__dir__` names a path inside the zip that `File` cannot open, and error messages lose their highlighted line. It is also the virtual filesystem Fledge rejects. Option 3 lost because a newcomer who zips a folder could not then play it, as LÖVE plays a `.love`. Option 4 lost on fidelity.

Fledge's rule governs how it runs an app's own program ([Fledge's ADR 081](https://github.com/setdef/Fledge/blob/trunk/doc/contributors/adr/081.md)). A game the player app opens is a file the player gives it, so how the player loads it is Lota's design, and option 1 keeps Fledge's reason for real files all the same.

Confidence: high that option 1 plays a game, low for the rest. The spike ran a game from an archive in Lota on Linux, its assets read through PhysFS and its Ruby unpacked. No player app exists yet. Whether Google Play would list one is unchecked.

### Consequences

- Good, because a game is shared and played as a LÖVE game is, in an app that matches LÖVE's.
- Good, because the game's Ruby sees real files, so it behaves as it does from its folder.
- Bad, because Lota builds, tests, and ships a player app for each desktop and Android with every release.
- Bad, because a first play waits while the archive unpacks, and the cache keeps a copy of each game played.
- Bad, because a game may use only the gems the player app ships.
- Bad, because a `.lota` is not a `.love`: LÖVE's app cannot play one, and LÖVE's tutorials about `.love` files need translating.
- Bad, because the player app carries no developer's signature, as LÖVE's carries none, so a player who downloads it meets the operating system's refusal for such apps and gets past it by hand.
- Bad, because unpacking meets limits a folder does not: on Windows, a long path fails where the person has not enabled long paths ([Microsoft's rules](https://learn.microsoft.com/en-us/windows/win32/fileio/maximum-file-path-limitation)), so the player refuses an archive it cannot unpack safely.
- Bad, because from 2027 an Android app installed outside Google Play needs a developer registered with Google ([Android's developer verification](https://developer.android.com/developer-verification)), so the maintainer registers to offer the Android player as LÖVE offers its own, as a download.

### Confirmation

Tests run a game from a `.lota` under `lota run` and in the player app, check that it reads its assets with `File`, and check that an archive with native code, or one the player cannot unpack safely, is refused with a message naming the entry.
