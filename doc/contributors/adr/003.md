# ADR 003: A Game Is a Folder, Configured and Driven by Methods on Lota

## Status
Accepted

## Date
2026-10-25

## Context

A LÖVE game is a folder. Its `main.lua` defines the game's callbacks as functions on the global `love` table (`function love.update(dt)`), and an optional `conf.lua` defines `love.conf(t)`, which LÖVE calls with a table of settings before it loads any module or opens the window (`vendor/love/src/modules/love/boot.lua`, lines 178–256). `love.run` then calls each callback that exists, skipping those that do not (`callbacks.lua`).

LÖVE code does more than define callbacks. Games call them (`love.draw()` to render into a canvas), check whether they exist (`if love.update then`), return from them early (`if paused then return end`), and wrap them: game-state libraries save the current `love.update` and install one that calls it and then their own. Lua passes a callback every argument LÖVE has, and the callback ignores the ones it does not declare (`function love.keypressed(key)` receives three).

A Lota game must translate from a LÖVE game line by line (ADR 001), and should read as Ruby.

## Decision

### 1. A game is a folder with `conf.rb` and `main.rb`

`lota run` runs the game in the current folder, or in the folder given (`lota run path/to/game`), as `love path/to/game` does. It loads `conf.rb` if present, calls `Lota.conf` with the settings, brings up the modules and the window, then loads `main.rb` and runs the loop, in the order `boot.lua` does.

### 2. Callbacks and `conf` are methods defined on `Lota`

Where Lua defines a function on the `love` table, Ruby defines a method on the `Lota` module:

```ruby
# conf.rb
def Lota.conf(t)
  t.title = "Asteroids"
  t.window.width = 1280
  t.window.fullscreentype = :exclusive
  t.modules.physics = false
end

# main.rb
def Lota.update(dt)
  return if paused
  player.move(dt)
end
```

Ruby methods give every behavior LÖVE code relies on, with nothing new to learn:

| LÖVE | Lota |
|---|---|
| `function love.update(dt)` | `def Lota.update(dt)` |
| `love.draw()` | `Lota.draw` |
| `if love.update then` | `if Lota.respond_to?(:update)` |
| `return` inside a callback | `return` inside the method |
| saving and wrapping `love.update` | prepending a module to `Lota.singleton_class` and calling `super` |

A block-based form (`Lota.update { |dt| ... }`) was considered and rejected, because `return` inside a stored block raises `LocalJumpError` once the block outlives the code that defined it, and Lua games return early from callbacks routinely.

### 3. Lota passes a callback only the arguments it declares

When Lota's loop calls a callback, it passes as many of LÖVE's arguments as the method declares, as Lua does, so `def Lota.keypressed(key)` receives the key alone. A method that takes a splat receives them all. A required parameter LÖVE does not pass receives `nil`, as Lua pads missing arguments with nil; an optional parameter LÖVE does not pass keeps the default its author wrote, because Lua has no defaults to follow and Ruby the language comes first. LÖVE passes no keywords, so a keyword parameter needs a default. A game that calls its own callback calls an ordinary Ruby method, with Ruby's usual argument checking.

### 4. `lota` is always available

Lota defines a private `Kernel#lota` that returns `Lota`, as Ruby's own `puts` and `require` are private `Kernel` methods, and each module has a lowercase accessor (`Lota.graphics` returns `Lota::Graphics`). So a tutorial's `love.` becomes `lota.` and nothing else changes: `def lota.update(dt)`, `lota.graphics.rectangle(...)`. Being private, `lota` adds no method to other objects' public interfaces; its only cost is reserving the name everywhere, as `puts` does. `Lota::Graphics.rectangle(...)` remains the idiomatic spelling, by ADR 001's rule 1.

### 5. The settings object keeps LÖVE's names

`t` is an object with readers and writers for each of `boot.lua`'s settings, nested as in Lua (`t.window.width`). Enum strings become symbols (ADR 001, rule 9). LÖVE's settings names are lowercase words run together (`fullscreentype`, `minwidth`, `usedpiscale`), and rule 13 converts only camelCase, so they keep LÖVE's spelling. A setting LÖVE does not know is accepted and ignored, as LÖVE ignores unknown keys in its table, so a translated `conf.lua` with keys of its own still runs. Reading a setting that was never set returns `nil`, as reading a missing key does in Lua.

### 6. The game folder is where `require` looks

`lota run` puts the game folder on `$LOAD_PATH`, as LÖVE's `require` searches the game's own folder, and leaves the working directory alone, as LÖVE does. A module the settings turn off is `nil` through its lowercase accessor (`lota.timer` with `t.modules.timer = false`), as `love.timer` is `nil` in LÖVE.

### 7. An error shows LÖVE's error screen, with a Ruby backtrace

When game code raises, Lota does what LÖVE's `love.errorhandler` does (`boot.lua` and `callbacks.lua`): it shows LÖVE's error screen in the game's window, with the error and a Ruby backtrace where LÖVE shows a Lua traceback, and a game may define `Lota.errorhandler` to replace it, as a LÖVE game may define `love.errorhandler`.

## Consequences

- Defining methods on another module's singleton is uncommon in Ruby code, but it is ordinary Ruby, and it makes a tutorial's `function love.x` and a Lota game's `def Lota.x` the same shape.
- The opt-in `lota/compat` adds a private `Kernel#love` returning `Lota`, beside its camelCase aliases (ADR 001, section 7), so LÖVE code runs unchanged. AGENTS.md's Trademarks section allows this one identifier because it must match LÖVE's API; it stays out of the core API.
- The core API has two spellings, `Lota::Graphics` and `lota.graphics`, for the same modules.
- Game-state libraries for Lota wrap callbacks with `prepend` rather than by reassigning a table field, which is the Ruby way to do it.
