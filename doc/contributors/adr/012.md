# ADR 012: Restart a Game by `exec` Now, and in the Same Process Later

## Context and Problem Statement

`love.event.restart` ends a LÖVE game and starts it again. `love.run` returns `"restart"`, and `love.cpp`'s `main` closes the Lua state and runs the game again in the same program, with the same arguments, passing the value on as `love.restart` (`src/love.cpp`, `runlove` and `main`). A fused game is fused again because the program is. Ruby cannot close the world a game defined: its classes, constants, and threads stay. How does a Lota game restart, under `lota run` and fused, on desktops and phones?

## Decision Drivers

- Restart in every case LÖVE does, fused games included.
- A fresh start: no classes, engine modules, audio devices, or threads left over.
- One way that works on macOS, Linux, and Windows.
- A path for phones, which forbid replacing a process, and for the App Sandbox on macOS 15, which kills a process that does.

## Considered Options

1. Replace the process with `exec`, running the program the process runs again, with the same arguments.
2. Restart in the same process, inside a `Ruby::Box` dropped on restart.
3. `exec RbConfig.ruby, $0, *ARGV`.

Options 1 and 2 were weighed on 2026-11-02, with a spike of option 2, and option 3 between 2026-11-03 and 2026-11-07.

## Decision Outcome

Chosen in three stages.

- **Now, on desktops:** option 1. The maintainer settled on 2026-11-07 that Lota restarts in every case LÖVE does, fused games included, since Lota ports LÖVE faithfully. Under `lota run` the program is Lota; in a fused game it is Fledge's launcher, which sets the app up as it first did.
- **Now, on phones and under the macOS 15 App Sandbox:** no restart. Phones forbid replacing a process, so a phone game ends when it restarts, as a quit ends it. Under the App Sandbox on macOS 15, the new image dies with `SIGTRAP` as it asks for a sandbox the process already has; on macOS 26 it restarts.
- **Later:** restart in the same process, as LÖVE does, on every platform, since phones forbid `exec` and the macOS 15 sandbox kills it.

Option 1 won over option 2 because `exec` gives the whole fresh start LÖVE gives without tracking what a game changed, and because the spike of option 2 failed. On Ruby 4.0.7 and 4.0.9, a dropped `Ruby::Box` that defined a named class or module was never freed, and every Lota box defines `Lota`, so five restarts left five engine copies with their audio devices and threads, about 36 MB each. The cause was not traced. Ruby documents boxes as experimental, means them to be freed, and has not called this behaviour intended; a related report, Bug #22403, is open. The box also loaded its own copy of the extension from a temporary directory, broke `$stdout` redirection, and could not keep the window. Lota revisits option 2 when a Ruby release frees such boxes and Lota can release its engine modules.

Option 3 lost because on Windows it runs the console Ruby, with the player's own settings, rather than the app. Fledge's `bin/ruby` hands it to the launcher on macOS and Linux, so running the launcher is the one way that holds on all three desktop systems.

Confidence: high for the desktop stage, low for the later one. A restart is tested under `lota run`, under `bundle exec`, and in a fused game on all five desktop platforms. No in-process restart has worked yet, and it also needs a way to release Lota's engine modules, as LÖVE's `lua_close` does, which Lota does not have.

### Consequences

- Good, because a restart on a desktop is a fresh start, and Lota needs no code to release its engine modules.
- Bad, because Windows has no `exec`: Ruby starts a new process and waits, so the old process stays, with any audio device it opened, until the new run ends.
- Bad, because a phone game cannot restart, and a sandboxed Mac game cannot restart on macOS 15, until the later stage lands.
- Bad, because the restart value crosses in an environment variable, so Lota encodes and checks it itself, and finds the program to run again on each platform as LÖVE's `getExecutablePath` does. Both are code the maintainer keeps per platform.

### Confirmation

- `test/restart_test.rb` checks how each kind of value crosses in the environment, and what is refused.
- `test/native/restart_run_test.rb` restarts a game under `lota run`, under `bundle exec`, and fused, through its launcher and through Ruby.
- CI's `fuse` job restarts `test/games/fuse` once on every platform, and checks that the run after it is the same process on macOS and Linux and a new one on Windows. The `windows-build` job restarts a game too.

## More Information

How each case restarts: [design/game.md](../design/game.md), "Restarting". Signing and the sandbox: [design/packaging.md](../design/packaging.md), "Signing on macOS".

A Claude Opus 5.5 study of Ruby's master branch on 2026-11-12 (`acc624e47b`) found why a dropped box stays alive, in two separate ways, neither of them Bug #22403, which is about a box keeping its own classes alive:

- A box that sets a constant on `Object`, as `class Foo` does, gets its own copy of `Object`'s class data, which `Object` marks strongly (`class.c`, lines 450-459; `gc.c`, line 3917). The constant's class marks its box (`gc.c`, lines 3918-3920), so the box is never unreachable. A fix makes those copies weak: roughly 200-400 lines across `gc.c`, `box.c`, `class.c`, and `internal/class.h`, and risky.
- A class defined from C is pinned as a permanent root (`class.c`, lines 1606-1610 and 1680-1692), and Rice defines every Lota class that way. Freeing a box that loaded an extension needs pins scoped to the box and the extension's copy unloaded early: a design change in Ruby, not a bug fix.

With RubyGems loaded, as by default, even an empty box is never freed, since each box loads RubyGems' prelude (`box.c`, lines 436-441). Nobody upstream was working on either leak, and a patched Ruby carried by Fledge was judged impractical. Two routes remain for the later stage. The nearer one keeps Lota and its engine loaded across a restart, as LÖVE's process stays while only its Lua state closes: Lota recreates its engine modules and runs the game's files with `Kernel#load(file, wrap_module)`, so the game's constants live in a module that is dropped, though changes to built-in classes and globals survive. The farther one is boxes, once Ruby frees them: a report of the first leak to Ruby, raising the second, would start that, and has not been filed.
