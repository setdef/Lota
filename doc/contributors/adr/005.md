# ADR 005: Change LÖVE's Engine Only Through Patch Files, as a Last Resort

## Status

Accepted

## Date

2026-10-24, widened from the physics patch alone on 2026-11-04

## Context and Problem

Lota runs LÖVE's engine (ADR 004), but sometimes the engine has to change. Lua reaches past the wrapper files in one module: LÖVE's Box2D classes hold a `lua_State*` for callbacks and user data, so they do not compile without Lua. Other changes fix defects in LÖVE that a game cannot avoid. Where should such changes live, and when are they allowed?

## Decision Drivers

- An upgrade of LÖVE stays a submodule bump, not a rebase.
- Every change to LÖVE's behavior is visible and justified.
- LÖVE accepts no contribution made with generative AI, so Lota cannot hand its fixes upstream.

## Considered Options

1. Patch files in Lota's repository, applied to a copy of the files at build time, only where Lota's own code cannot do the work.
2. Edit the files in `vendor/love` and rebase the edits on each upgrade.
3. Fork LÖVE.

## Decision Outcome

Chosen: option 1. Each patch states in its header why nothing outside LÖVE's file can do the work, and is dropped once LÖVE no longer needs it. A patch for a defect in LÖVE has beside it the report Lota would file upstream. Keeping patches few and small is a goal worth measuring. A fork stays a separate decision, and the maintainer makes it.

### Consequences

- Good, because `vendor/love` is never written to, so an upgrade bumps the submodule and reapplies a short list of patches.
- Good, because each change carries its reason in its header.
- Bad, because a patch can stop applying when LÖVE changes the file under it, and someone has to port it.
- Bad, because a fix that belongs upstream stays in Lota for as long as LÖVE needs it, since Lota cannot offer it to LÖVE.
