# ADR 005: Change LÖVE's Engine Only Through Patch Files, as a Last Resort

## Context and Problem Statement

Lota runs LÖVE's engine ([ADR 004](004.md)), but sometimes the engine has to change. Lua reaches past the wrapper files in one module: LÖVE's Box2D classes hold a `lua_State*` for callbacks and user data, so they do not compile without Lua. Other changes fix defects a game cannot avoid, such as a Mesh whose vertex data is allocated with `new[]` and freed with `delete`. Where do such changes live, and when are they allowed?

## Decision Drivers

- An upgrade of LÖVE stays a submodule bump plus a short list of changes, not a rebase of a branch.
- Every change to LÖVE's behavior is visible and carries its reason.
- LÖVE accepts no contribution made with generative AI tools (its README, Contributing), so Lota cannot hand its fixes upstream.
- Upkeep that one maintainer can carry.

## Considered Options

1. Patch files in Lota's repository, applied to a copy of the files at build time, only where Lota's own code cannot do the work.
2. Fork LÖVE, carry the changes as commits, and rebase them on each upgrade.
3. Leave LÖVE's files alone, and give the physics module a stand-in for the parts of Lua's C API it calls.

Options 1 and 2 were weighed on 2026-10-24, and option 3 on 2026-10-27.

## Decision Outcome

Chosen: option 1, because an upgrade of LÖVE then stays a submodule bump rather than a rebase, and `vendor/love` stays LÖVE's own commit. That is why option 2 lost. The decision first covered the physics module alone. On 2026-11-04 it widened to any change Lota's own code cannot make, because of the Mesh defect above: no code outside LÖVE's file can change how a private pointer is freed. Each patch states in its header why nothing outside LÖVE's file can do the work, and is dropped once LÖVE no longer needs it. A patch for a defect in LÖVE has beside it, in `doc/contributors/upstream/`, the report Lota would file. A fork stays a separate decision, and the maintainer makes it.

Option 3 lost on 2026-10-27, when the physics patch was written: a stand-in would have kept Lua's shape, a stack and its references, inside Lota's binding.

Confidence: medium. The mechanism works: four patches apply on every platform CI builds (`physics.patch`, which changes 28 files of LÖVE's Box2D module and adds one; `mesh.patch`; `lz4.patch`; and, for Android alone, `vulkan_present.patch`). The cost of an upgrade is unknown, since none has happened yet.

### Consequences

- Good, because `vendor/love` is never written to, so an upgrade bumps the submodule and reapplies a short list of patches.
- Good, because each change carries its reason in its header, and a reviewer reads Lota's whole difference from LÖVE in four files.
- Bad, because a patch stops applying when LÖVE changes the lines under it, and the maintainer ports it by hand. `physics.patch` alone is about 2,000 lines, so an upgrade that touches LÖVE's physics module is the costly case.
- Bad, because a fix that belongs upstream stays in Lota for as long as LÖVE needs it, since Lota cannot offer it to LÖVE.
- Bad, because every build machine carries a `patch` program and keeps LÖVE's line endings as they are. CI's Windows job installs `patch` and turns off Git's line-ending conversion, or `physics.patch` does not apply.

### Confirmation

- CMake applies each patch when it configures, and stops the build when one fails, saying the patch does not apply and to update it for this LÖVE (`ext/lota/engine/CMakeLists.txt`). Every gate and CI build configures, so a stale patch fails the first build after an upgrade.
- Tests fail without each patch: the sanitized suite (`rake test:native`) stops on the Mesh and LZ4 defects, `test/tasks/vulkan_present_patch_test.rb` checks the Android patch, and the physics tests in `test/native/` exercise the physics patch.
- Review checks each new patch for its reason in the header and its report in `doc/contributors/upstream/`, as AGENTS.md asks.
