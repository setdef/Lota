# Plan 001: Ship a Gem That Does Nothing, Then Grow It One Game at a Time

ADR 001 decides what Lota is: a modified build of LÖVE's C++ engine, pinned at `vendor/love`, driven by Ruby through Rice, with LÖVE's API translated by rule. This plan decides the order of the work.

The work grows in vertical slices, not layers. The first slice is a walking skeleton: the thinnest path through every layer, from `gem install` to pixels on a canvas, shipped through the same pipeline every later change will use. After that, each story adds the engine surface one more piece of real LÖVE code needs, and is done when that code behaves the same in Lota as in LÖVE.

## What "correct" means: code other people wrote

Every acceptance test runs Lua that someone other than this project wrote, translated to Ruby by ADR 001's rules, and compares the result with what LÖVE does.

**Lövetest.** LÖVE ships its own test suite in `vendor/love/testing`: 364 test functions in 7,295 lines of Lua covering every module, written for LÖVE 12, with 63 expected images for graphics tests. A story that binds a function also translates and passes Lövetest's tests for it. Translate from the copy in `vendor/love`, which ships in LÖVE's repository under its Zlib license, and mark the translation with SPDX snippets. Lövetest's standalone repository (`ellraiser/love-test`) declares no license, so do not translate from it, and confirm this reading with LÖVE's maintainers before the translation ships.

**Open-source games.** A game qualifies only when its code and every one of its assets are under free licenses compatible with AGPL-3.0-or-later, so that it can also serve as a demo. These qualify:

| Game | License | Targets | Size | What it exercises |
|---|---|---|---|---|
| [plinkr/flash-blip](https://github.com/plinkr/flash-blip) | MIT; no external assets | LÖVE 11.5 | 42 Lua files | About 1,300 calls a frame in play and 2,600 in attract mode, from shapes drawn one rectangle per pixel; also shaders, canvases, generated audio, `love.thread`, and LuaSocket HTTP, so it joins after the `love.thread` story. |
| [whyboris/Gravity-Wars](https://github.com/whyboris/Gravity-Wars) | MIT; its one font is MIT | LÖVE 11.3 | 7 Lua files | Shapes, input, a TrueType font, two PNG images, the system mouse cursor, antialiased canvases, and `math.random` seeded from the clock. |
| [noooway/love2d_arkanoid_tutorial](https://github.com/noooway/love2d_arkanoid_tutorial), chapter 1 | MIT; no assets | LÖVE 0.10 | 7 snapshots (1-01 to 1-A) | Shapes, input, and collisions, growing one snapshot at a time. Snapshot 1-B is left out: it calls a function before declaring it, so it fails on every LÖVE version. Later chapters add images and sounds whose licenses are not stated, so they do not qualify. |
| [Nightwolf-47/KleleAtoms](https://github.com/Nightwolf-47/KleleAtoms) | MIT; its 29 images and 3 sounds are in the repository its license covers | LÖVE 11.3 | 11 Lua files | Images, quads, and canvases, text in LÖVE's default font, the mouse, window modes, sound effects, and LÖVE's version warning, which its `t.version` of 11.3 brings up on LÖVE 12. It also reads and saves its settings and a game in its save directory (`t.identity`), through `love.filesystem.getInfo`, `read`, `write`, `lines`, and `remove`. |

No qualifying game uses `love.physics` yet; the physics story uses Lövetest's physics tests until one turns up. Candidates whose assets are not free were left out.

LÖVE 12 is unreleased, so these games target LÖVE 11 or older. All of them run on the pinned commit unchanged. A game that ever needs changes gets only the renames `vendor/love/changes.txt` lists, kept as a patch file beside the game, never a rewrite.

Lua libraries that LÖVE bundles but that are not engine code, such as LuaSocket and LÖVE 12's HTTPS module, translate to their Ruby standard library counterparts (`Socket`, `Net::HTTP`), as Lua tables translate to Ruby objects.

The harness runs each game as a player would, in both engines:

- **Dialogs** such as LÖVE's version warning are dismissed by pressing Return, so both engines must show them. The harness presses the dialog's default button, the one Return presses, from inside the game's own process, as it pushes key events into SDL's queue: System Events, which would press Return from another process, needs Accessibility permission, which a developer's shell may not have and a CI runner may not grant.
- **Saved files** go to a home directory of each run's own, LÖVE's and Lota's, so a game that saves starts each run with nothing saved, and the two runs' saves can be compared. Sounds play into OpenAL Soft's wave file writer there, as LÖVE's CI plays Lövetest's, so runs make no sound and play alike with or without an audio device.
- **The mouse** is scripted as keys are: the pointer is held at the script's latest position with `love.mouse.setPosition`, which updates SDL's mouse state, and clicks push SDL's button events at it. A click does not reach `love.mouse.isDown`, since SDL keeps the buttons that are down to itself. Anything else that moves the system's pointer during a run, such as a person, can change what the game sees.
- **Windows stay in the background**, so a run takes no keyboard focus from the person at the computer: both engines start with SDL's hints that keep windows from activating their program, and the code that dismisses dialogs keeps the program from ever being activated, since AppKit activates a program that shows one.
- **The deprecation overlay** stays on and is compared while it is clearly visible. It times out after 20 seconds of wall-clock time (`Deprecations.cpp:60-66`), not game time, so frames near the cutoff are not compared.
- **Random numbers** come from LÖVE's own generator in both runs: the Lua side's `math.random` is pointed at `love.math.random` with a fixed seed and a fixed clock, and the Ruby translation calls `Lota::Math.random`. Both sides seed the generator with the clock before the game's `load`, since LÖVE seeds it from the real time, and `love.timer.getDelta` returns the fixed `dt`. Idiomatic translations use Ruby's own `rand`, which cannot match Lua's.
- **Network requests** a game makes go to a local stand-in, never to the network.

Fixtures are pinned submodules under `test/fixtures/`, excluded from the gem. Their assets stay under their own licenses and are never redistributed in the gem.

## Spikes: answer the risky questions with throwaway code

Each spike is a small experiment that answers one question, then gets thrown away. The answer goes in this plan.

1. **Does LÖVE build without Lua? Yes.** With the exclusions in ADR 001, section 1, plus `modules/physics`, the engine links as one static library with no Lua symbols, against `love2d/love-apple-dependencies` on its `main` branch (the branch LÖVE's own CI uses). A small C++ program opened a window under Metal and OpenGL, cleared it, and read the pixels back: the window and a 16×16 canvas both matched their clear colors.
2. **Does Rice load that engine into Ruby, on the main thread?** The same window, opened from `ruby -e`, on macOS, where SDL needs the main thread.
3. **Which fixture games run on the pinned LÖVE? All of them, unchanged.** `love` built from `vendor/love` passes Lövetest (349 of 349 on Metal). The spike built it with LÖVE's CMake while Xcode was broken; the parity harness builds it as LÖVE's own macOS CI does, with Xcode, raising the deployment target to macOS 12.0 because current Xcode refuses LÖVE's 10.15. At 330 ns per bound call, binding cost stays under 0.6% of a 120 Hz frame for the arkanoid snapshots, Gravity-Wars, and KleleAtoms, and reaches 5 to 12% for flash-blip. Play each game long enough to know what correct looks like.
4. **How long does a clean build take?** 49 seconds on a 10-core M1 Max, and 0.02 seconds for a rebuild with no changes, which is fast enough to build on every change. CI runners remain to be measured.

## The walking skeleton: a gem that clears a canvas

The skeleton does nothing a player would notice. It clears a 16×16 canvas to yellow, which is Lövetest's `love.test.graphics.clear`, and compares the result with LÖVE's expected image, `love.test.graphics.clear-1.png`. Doing that from an installed gem forces every decision the rest of the project depends on:

- **The engine build:** the source lists from spike 1, regenerated by a Rake task whenever the submodule moves, which fails if a listed file disappears.
- **The extension:** a Rice extension, `Lota::Native`, compiled by rake-compiler's `Rake::ExtensionTask`, with `extconf.rb` driving CMake.
- **The memory rule:** `love::Object` retained when Ruby wraps it and released when Ruby frees the wrapper. `love::Object` counts references per object but keeps no count of live objects, so a test binds a test-only subclass that counts its own constructions and destructions, creates and drops a million wrappers, runs the garbage collector, and asserts that every object not destroyed still has a live Ruby wrapper. Ruby's collector scans stacks conservatively, so a stale word can keep a few wrappers alive, and an exact count cannot be guaranteed.
- **The game loop:** the smallest faithful port of `love.run` from `boot.lua` and `callbacks.lua` that runs the test, with SPDX snippets (`Zlib`) and citations of the lines ported.
- **The entry point:** an executable that runs a game, as `love` does. How a Lota game is laid out and configured is a design question for the maintainer; the skeleton needs only enough answer to run one test.
- **The bindings:** `newCanvas`, `setCanvas`, `clear`, and `readbackTexture`, plus `newImageData` and `newFileData` for the comparison, written by hand. The generator comes later, when hand-written bindings show the pattern.
- **The gates:** RuboCop, RubyCritic, Steep with no `untyped`, signature parity, RDoc coverage, REUSE, and the package check, plus C++ gates, all from the first commit:
  - `cpp:format`: `clang-format --dry-run -Werror`.
  - `cpp:tidy`: `clang-tidy` with warnings as errors, from the `compile_commands.json` CMake writes.
  - `cpp:no_nolint`: no `NOLINT` outside entries in `cpp_exceptions.rb`, through the existing `Lint` class.
  - `test:native`: the test suite rebuilt with AddressSanitizer and UndefinedBehaviorSanitizer.
  - `-Wall -Wextra -Werror` on Lota's own C++; LÖVE's sources build with `-w` (ADR 001, section 1).
  - RBS for `Lota::Native`, written by hand for now because Rice's `bin/rice-rbs.rb` produces invalid, incomplete signatures (spike 2); the binding generator (story 2) will generate it, with a gate that fails on any difference.
  - `clang-format`, `clang-tidy`, and `cmake` in `mise.toml`.
- **The package:** `package:check` loads the compiled extension from the built gem, and `package:install` installs the precompiled gem into an empty `GEM_HOME` and runs games from it. Lota ships a precompiled gem per platform, carrying the compiled extension, the frameworks it loads, and the license texts they need in `LICENSES/`, recorded with REUSE as the rest of the repository is, with the credit FreeType's license asks for in the README's licensing section; the source gem refuses to build and points to it, because building would mean shipping LÖVE's sources and expecting a C++ toolchain at install time. On macOS, `love-apple-dependencies` provides dynamic, universal frameworks with `@rpath` install names and a minimum of macOS 11.0, and SDL3's ad-hoc signature is already invalid as checked out, so the build thins, re-signs, and verifies each framework it ships. The binaries run on macOS 11.0 and newer; Lota supports macOS 15 and newer (ADR 002). The skeleton needs only Apple Silicon macOS.
- **Continuous integration:** GitHub Actions runs the default Rake task on every push, as LÖVE's own CI runs Lövetest (`vendor/love/.github/workflows/main.yml`): on macOS runners with the normal video driver, because SDL's offscreen driver cannot create a Metal or OpenGL context on macOS, and later on Linux under Xvfb. The skeleton runs on a macOS runner; Linux and Windows runners join once it passes there, built against `love2d/megasource`. The harness dismisses dialogs from inside the game's process, which needs no Accessibility permission, so CI needs none either.
- **Delivery:** CI builds the gem, installs the built `.gem` into an empty `GEM_HOME` on a fresh runner, and runs the test from there. Nothing is published to RubyGems until the library is good enough to deserve the name `lota`, which will not be known until well after the skeleton.

**Done when:** on every push, a fresh CI runner installs the built gem, runs the translated `love.test.graphics.clear`, and it passes against LÖVE's expected image; and every gate passes with zero errors and zero warnings.

## Stories: one piece of real LÖVE code at a time

Each story names a piece of fixture code, such as a Lövetest module's tests, a game, or a chapter of the arkanoid tutorial, and grows Lota until that code behaves the same. Every story follows the same steps:

1. List the LÖVE functions the fixture calls that Lota does not bind yet.
2. Run the collision report over them: every function that fits no rule in ADR 001's table, or more than one. Each collision goes to the maintainer as a question, and its answer becomes a new rule, never a one-off.
3. Bind the functions, through the generator once it exists.
4. Translate the fixture to Ruby by the rules, both verbatim through `lota/compat` and idiomatic, once `lota/compat` exists.
5. Translate and pass Lövetest's tests for every function the story bound.

A story is done when the fixture's graphics match LÖVE frame by frame (screen read back each frame with a fixed `dt` and compared), Lövetest's tests for its functions pass, the gate passes, and CHANGELOG.md says what game developers can now do.

The first stories, in an order the maintainer can change at any planning session:

1. **Shapes and the keyboard.** The arkanoid tutorial's first snapshot, then Gravity-Wars. This story first exercises `love.load`, `love.update`, `love.draw`, input, and a window that stays open.
2. **The binding generator.** By now the hand-written bindings show the pattern. Write a generator that reads `wrap_*.cpp` files and applies the rule table and a short exceptions file, then regenerate the existing bindings with it and confirm nothing changes. Generated code is marked as generated and never edited by hand. The collision report becomes the generator's report mode. `File:open`, which returns `false` on failure and so collides with rule 11, is already on it.
3. **Images, text, and SpriteBatch.** KleleAtoms' images and Gravity-Wars' TrueType font. Benchmark 10,000 `draw` calls a frame, and the Array allocations that rules 4 and 6 add, under the interpreter, YJIT, and ZJIT. Record the numbers here. Build a Ruby-side batcher, or allocation-free variants, only if the numbers say to. SpriteBatch's acceptance test is Lövetest's, since no fixture game uses it; its array-texture part waits for `newArrayImage`, whose `ArrayImage ===` rule 2 has not settled. KleleAtoms runs in the reference LÖVE and, translated to Ruby (`test/games/klele_atoms`), in Lota, its version warning dismissed, played with a scripted mouse through the menu, a game against the computer, a chain reaction, the pause menu's Save & Quit, and Escape: all 399 frames it draws match LÖVE's, it prints what LÖVE prints, and the settings and the game it saves are LÖVE's, byte for byte. Rule 4 now returns every function's several results as an Array, on failure too, and rule 10 a returned record as a frozen `Data`, which translate `getInfo`, `read`, and `write`; the generator applies rule 4 to every binding it writes. Done, but for the window's icon from `t.window.icon`, which Lota's boot does not set yet and no frame shows.
4. **Sound.** KleleAtoms' sound effects, which play in Lota since story 3. The precompiled gem carries OpenAL Soft 1.24.3 as a framework of its own, with the release's source archive and its licenses (`ext/lota/licenses.rb`), as its license asks. Compare decoded sample buffers where the output can be compared offline. OpenAL Soft's wave writer, which both parity runs play into, mixes on the wall clock in steps of 20 milliseconds: in KleleAtoms' run each sound that plays alone is the same, sample for sample, in LÖVE's file and Lota's, but where each starts depends on how fast each engine ran, and sounds that overlap, as the chain reaction's do, add up differently from run to run, so the files themselves cannot be compared until the mixer runs on game time, as a loopback device rendered once a frame would.
5. **Physics.** Lövetest's 26 physics tests, and the first qualifying game that uses `love.physics` if one turns up. This story writes the physics patch, replacing the `lua_State*` callbacks and userdata in `src/modules/physics/box2d/` with a callback interface Ruby implements, kept small and applied at build time. Lövetest's physics tests do not record motion over time. When a qualifying physics game turns up, its story adds trace comparison: each body's position and each contact, frame by frame, from both engines.

Ractor readiness is a standard every story meets, not a story of its own: each engine object a story binds is marked shareable when LÖVE guards it with its own lock, and each plain value can be frozen to cross Ractors, and the native modules LÖVE's thread module allows off the main thread are marked Ractor-safe as they arrive. The Ractor counterpart of `love.thread` becomes a story when a fixture needs it.

## Design questions, settled as stories reach them

These have no LÖVE behavior to copy. Each is talked through with the maintainer when a story first needs it, then recorded in an ADR. None is decided ahead of time.

- Whether `.love` archives can hold Ruby. How a game is laid out and configured is settled by ADR 003.
- The Ruby callback shape for physics contacts.
- The Ractor counterpart of `love.thread` and its channels.

## Open questions

- **Upgrading LÖVE.** When 12.0 is tagged, move the pin to the tag, regenerate the source lists and bindings, rerun every fixture, and write down the procedure the first time.
