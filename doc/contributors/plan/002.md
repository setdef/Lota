# Plan 002: Bind the Rest of LÖVE, Then Ship Games

ADR 001, section 1, binds the whole engine. Plan 001 bound only what its five stories needed: about 325 of the roughly 1,100 functions and methods in the binding generator's name table, and about 100 of Lövetest's roughly 360 tests. A game that calls anything else stops with a `NoMethodError`, however well the rest of Lota matches LÖVE. This plan binds the rest, then lets a developer ship what they build.

Plan 001's way of working still holds: vertical slices, each done when code someone else wrote behaves in Lota as it does in LÖVE, through the same gate, on every platform with a gem.

## What done means

Every one of Lövetest's tests (`vendor/love/testing/tests`), translated by ADR 001's rules, passes in Lota and from the installed gem, on every platform Lota ships a gem for, against the expected images LÖVE's own CI compares with. Where Lövetest skips a test on a platform, Lota skips it there too, for the same reason. Lövetest counts as the acceptance test for each module, and published games stay the acceptance test for behavior over time.

## How bindings are written

The generator writes every binding it can, and each story extends it before binding by hand. A binding that stays hand-written records why in `ext/lota/bindings.rb`, as now. A measurement on 2026-10-28 found that moving the wrap logic into Ruby over directly bound engine methods would remove only about 40 to 55 percent of the C++. It would cost nothing per call only if every binding were written with care, and Rice's enum values would stop being shareable between Ractors. So bindings stay in C++, and each story first teaches the generator the hand-written patterns it meets, of which about 80 of the 138 reduce to plain bindings.

The first such step moved 27 of them. The generator now returns the engine object a wrap function pushes, and gives Ruby the reference of one it made and released; returns nil where a function pushes nil or returns nothing; makes the checks of LÖVE's guard helpers, such as `luax_checkgraphicscreated`, where they are called; reads a count of the arguments as whether one is given; and types the declarations, C arrays, and numbers it could not before. Several of the 80 turned out not to reduce: the joint constructors that choose their form by `lua_gettop` and `Body:applyForce` read one position as a number or a boolean, and `lua_gettop` counts an argument given as nil, which Rice passes as none, so they keep their Array of arguments until the generator can write one. The error messages' name table went to Ruby in the same session: `Lota::ErrorMessage` rewrites a message as Ruby raises it, from a table the generator writes as a frozen Hash.

## Stories

The order follows what games call most. Each story's Lövetest module is its acceptance test.

A real game now sets the order ahead of story 1's remaining slices. The maintainer's deckbuilder runs on Lota, and what it calls comes first: (1) finish slice 2; (2) Font's metrics, and the fix that makes `t.window.highdpi` work as it still does in LÖVE 12; (3) `ImageData#encode` and `capture_screenshot`, so a game can save a frame; (4) slice 3's mipmaps, filters, and stencils; and (5) audio from memory and positional audio. Then the order below resumes. Each item still lands with the Lövetest tests it covers.

1. **The rest of graphics.** Lövetest's 109 graphics tests: shaders, meshes, text objects, stencils, every texture and canvas format, blend and depth state, and the remaining drawing calls. This is the module games lean on most, and the one flash-blip needs. 26 of them were translated before this story. The other 83 come in six slices, each a change of its own, in an order where each builds on the ones before:
    1. **Drawing state and primitives**, 33 tests: `points`, `polygon`, `discard`, `getBackgroundColor`, `setBackgroundColor`, `getBlendMode`, `setBlendMode`, `getCanvas`, `getColorMask`, `setColorMask`, `getDepthMode`, `setDepthMode`, `getFont`, `getFrontFaceWinding`, `getLineJoin`, `setLineJoin`, `setLineStyle`, `setLineWidth`, `getMeshCullMode`, `setMeshCullMode`, `getPointSize`, `getScissor`, `setScissor`, `intersectScissor`, `getStackDepth`, `getStencilState`, `setStencilState`, `isActive`, `isGammaCorrect`, `isWireframe`, `setWireframe`, `reset`, and `getRendererInfo`. They bind the state setters and getters with no object of their own, and the two drawing calls that read coordinates as `line` does. `setStencilState` draws into `setCanvas({canvas, stencil = true})`, a table of targets and options, so it came with slice 3.
    2. **Transforms, coordinates, and the renderer's queries**, 21 tests: `applyTransform`, `inverseTransformPoint`, `replaceTransform`, `rotate`, `shear`, `transformPoint`, `resetProjection`, `getDPIScale`, `getDimensions`, `getWidth`, `getHeight`, `getPixelDimensions`, `getPixelWidth`, `getPixelHeight`, `getStats`, `flushBatch`, `getSupported`, `getSystemLimits`, `getTextureFormats`, `getTextureTypes`, and `captureScreenshot`. They bring `love.math`'s Transform forward from story 3, `push`'s form that applies one, `setProjection`, and `love.window.getMode`. `getStats`, `getSupported`, `getSystemLimits`, `getTextureFormats`, and `getTextureTypes` return tables as records, which rule 10 makes frozen `Data` that also answers `[]`, so `getTextureTypes`' `2d` reads `types["2d"]`, as in Lua. Twenty are translated, with `love.math`'s Transform and its whole test, `Transform`'s `__mul` as `*`, and `affine2d_transform?` and `dpi_scale` spelled by rule 13. `captureScreenshot` is bound in its function and filename forms, the function as a block or anything that answers `call` (rule 12), and its Channel form waits for story 7; its Lövetest test compares the window with what Lövetest's own `love.draw` shows, so it waits for a port of that screen.
    3. **Textures, canvases, and readback**, 10 tests: `Canvas`, `Image`, `newCanvas`, `newImage`, `newArrayImage`, `newCubeImage`, `newVolumeImage`, `drawLayer`, `setCanvas`, and `draw`. They bind texture settings (mipmaps, formats, readable, depth and stencil), the Texture methods for filters, wrapping, mipmaps, and pixels, `readbackTexture`'s slice, mipmap, and rectangle, `setCanvas`'s forms with several targets and options, and `draw` with a Transform. Rule 10 settles the table form of `setCanvas` as keywords, `set_canvas(canvas, stencil: true)` and `set_canvas([a, b], depth: true)`, with `canvas=` kept for the plain form, so slice 1's `setStencilState` is translated with this slice. All ten are translated, `Canvas` but for its two checks that draw with a shader, which wait for slice 5, along with `ArrayImage`, `CubeImage`, and `VolumeImage` as modules whose `===` asks a texture's type, as rule 2 makes `Canvas`. Rule 10 also gives each target of the table of tables its options as `[texture, layer: 2, mipmap: 1]`, and rule 4 makes `getCanvas` return an Array on every path, `[]`, the canvases, or one Array of the targets, so slice 1's `canvas` changed with it.
    4. **Fonts and text**, 4 tests: `Font`, `Text`, `newTextBatch`, and `newImageFont`. Font's metrics and fallbacks came first, for the game that sets the order above, with `Font`'s test but for its check of fallbacks, which draws with `newImageFont`; this slice binds image fonts and TextBatch, and finishes that test.
    5. **Shaders**, 6 tests: `Shader`, `newShader`, `validateShader`, `setShader`, `getShader`, and `setFrontFaceWinding`. They bind Shader, its uniforms through `send` and `sendColor`, and `ImageData.new`, which `setFrontFaceWinding`'s shader draws from.
    6. **Meshes, buffers, and particles**, 7 tests: `Buffer`, `ShaderStorageBuffer`, `Mesh`, `newMesh`, `drawInstanced`, `ParticleSystem`, and `newParticleSystem`. They bind Buffer and its formats, Mesh and its vertex attributes, instanced drawing, and ParticleSystem, on the textures and shaders the slices before them bind.

    Lövetest's `Video` and `newVideo` tests belong to story 6, which brings Theora.
2. **Window, keyboard, timer, system, event, and love.** Their 75 tests: text input and key repeat, the remaining window modes and displays, the timer's sleep and averages, the clipboard and power state, the rest of the event queue, and `love.getVersion` and its kin.
3. **Math, data, image, and font.** Their 44 tests: transforms, Bézier curves, triangulation, compression and hashing, encoding images, and rasterizers and glyph data. Lövetest's `ImageData` test came first, for the game that sets the order above, with `ImageData:encode`, `paste`, and the start of `love.filesystem.openFile`'s File, whose other methods wait for story 4.
4. **The rest of audio and filesystem.** Their 66 tests: queueable sources, effects, recording, positional audio, and the filesystem's mounting, files opened for writing, and directory listing. Audio from memory and positional audio came first, for the game that sets the order above: `Source.new` of a `FileData`, a `Decoder`, or a `SoundData`, Source's place in space, its distances, rolloff, cone, and units of time, and the listener's position, orientation, velocity, Doppler scale, and distance model, with ten of audio's tests and `Source`'s but for its queueable source, filter, and effect.
5. **Joystick, touch, and sensor.** Their 13 tests, run as LÖVE's own CI runs them, with no hardware attached, plus the gamepad mapping database.
6. **Video.** Lövetest's two video tests. Theora is a new library in the gem, so it is licensed under REUSE as every other library is.
7. **Threads.** The Ractor counterpart of `love.thread` and its channels, which ADR 001, section 6, leaves to this point. It is a design question for the maintainer first, then Lövetest's five thread tests.
8. **flash-blip.** The fixture Plan 001 held back: shaders, canvases, generated audio, `love.thread`, and HTTP through `Net::HTTP` where it uses LuaSocket. It is also the heaviest binding load of any fixture, at 1,300 to 2,600 calls a frame, so it tests ADR 001, section 8's decision to keep Rice.
9. **`lota fuse`.** ADR 002: a prebuilt runtime per platform, Ruby from rv-ruby on macOS and Linux, and a game written into it the way LÖVE fuses one, signed on macOS. Fused games save where LÖVE's fused games save (ADR 003, section 8). Windows follows ADR 002, section 4's spike.

Plan 001's platform stories (Windows, Intel Macs, and phones and tablets) continue alongside these, and each new module lands on every platform that has a gem.

## Design questions, settled as stories reach them

- The Ractor counterpart of `love.thread` (story 7).
- Whether `.love` archives can hold Ruby (story 9).

## Open questions

- **The gate's length.** A clean local gate takes 12 to 15 minutes and CI's about 30, and every story adds to both. When either gets in the way of small steps, split the slow tests into their own task without dropping any from the gate.
