# Plan 002: Bind the Rest of LÖVE, Then Ship Games

ADR 001, section 1, binds the whole engine. Plan 001 bound only what its five stories needed: about 325 of the roughly 1,100 functions and methods in the binding generator's name table, and about 100 of Lövetest's roughly 360 tests. A game that calls anything else stops with a `NoMethodError`, however well the rest of Lota matches LÖVE. This plan binds the rest, then lets a developer ship what they build.

Plan 001's way of working still holds: vertical slices, each done when code someone else wrote behaves in Lota as it does in LÖVE, through the same gate, on every platform with a gem.

## What done means

Every one of Lövetest's tests (`vendor/love/testing/tests`), translated by ADR 001's rules, passes in Lota and from the installed gem, on every platform Lota ships a gem for, against the expected images LÖVE's own CI compares with. Where Lövetest skips a test on a platform, Lota skips it there too, for the same reason. Lövetest counts as the acceptance test for each module, and published games stay the acceptance test for behavior over time.

## How bindings are written

The generator writes every binding it can, and each story extends it before binding by hand. A binding that stays hand-written records why in `ext/lota/bindings.rb`, as now. A measurement on 2026-10-28 found that moving the wrap logic into Ruby over directly bound engine methods would remove only about 40 to 55 percent of the C++. It would cost nothing per call only if every binding were written with care, and Rice's enum values would stop being shareable between Ractors. So bindings stay in C++, and each story first teaches the generator the hand-written patterns it meets, of which about 80 of the 138 reduce to plain bindings.

The first such step moved 27 of them. The generator now returns the engine object a wrap function pushes, and gives Ruby the reference of one it made and released; returns nil where a function pushes nil or returns nothing; makes the checks of LÖVE's guard helpers, such as `luax_checkgraphicscreated`, where they are called; reads a count of the arguments as whether one is given; and types the declarations, C arrays, and numbers it could not before. Several of the 80 turned out not to reduce: the joint constructors that choose their form by `lua_gettop` and `Body:applyForce` read one position as a number or a boolean, and `lua_gettop` counts an argument given as nil, which Rice passes as none, so they keep their Array of arguments until the generator can write one. The error messages' name table went to Ruby in the same session: `Lota::ErrorMessage` rewrites a message as Ruby raises it, from a table the generator writes as a frozen Hash.

## Stories

The order follows what games call most. Each story's Lövetest module is its acceptance test.

A real game now sets the order ahead of story 1's remaining slices. The maintainer's deckbuilder runs on Lota, and what it calls comes first: (1) finish slice 2; (2) Font's metrics, and the fix that makes `t.window.highdpi` work as it still does in LÖVE 12; (3) `ImageData#encode` and `capture_screenshot`, so a game can save a frame; (4) slice 3's mipmaps, filters, and stencils; and (5) audio from memory and positional audio. Then the order below resumes. Each item still lands with the Lövetest tests it covers.

1. **The rest of graphics.** Lövetest's 109 graphics tests: shaders, meshes, text objects, stencils, every texture and canvas format, blend and depth state, and the remaining drawing calls. This is the module games lean on most, and the one flash-blip needs. 26 of them were translated before this story. The other 83 come in six slices, each a change of its own, in an order where each builds on the ones before:
    1. **Drawing state and primitives**, 33 tests: `points`, `polygon`, `discard`, `getBackgroundColor`, `setBackgroundColor`, `getBlendMode`, `setBlendMode`, `getCanvas`, `getColorMask`, `setColorMask`, `getDepthMode`, `setDepthMode`, `getFont`, `getFrontFaceWinding`, `getLineJoin`, `setLineJoin`, `setLineStyle`, `setLineWidth`, `getMeshCullMode`, `setMeshCullMode`, `getPointSize`, `getScissor`, `setScissor`, `intersectScissor`, `getStackDepth`, `getStencilState`, `setStencilState`, `isActive`, `isGammaCorrect`, `isWireframe`, `setWireframe`, `reset`, and `getRendererInfo`. They bind the state setters and getters with no object of their own, and the two drawing calls that read coordinates as `line` does. `setStencilState` draws into `setCanvas({canvas, stencil = true})`, a table of targets and options, so it came with slice 3.
    2. **Transforms, coordinates, and the renderer's queries**, 21 tests: `applyTransform`, `inverseTransformPoint`, `replaceTransform`, `rotate`, `shear`, `transformPoint`, `resetProjection`, `getDPIScale`, `getDimensions`, `getWidth`, `getHeight`, `getPixelDimensions`, `getPixelWidth`, `getPixelHeight`, `getStats`, `flushBatch`, `getSupported`, `getSystemLimits`, `getTextureFormats`, `getTextureTypes`, and `captureScreenshot`. They bring `love.math`'s Transform forward from story 3, `push`'s form that applies one, `setProjection`, and `love.window.getMode`. `getStats`, `getSupported`, `getSystemLimits`, `getTextureFormats`, and `getTextureTypes` return tables as records, which rule 10 makes frozen `Data` that also answers `[]`, so `getTextureTypes`' `2d` reads `types["2d"]`, as in Lua. Twenty are translated, with `love.math`'s Transform and its whole test, `Transform`'s `__mul` as `*`, and `affine2d_transform?` and `dpi_scale` spelled by rule 13. `captureScreenshot` is bound in its function and filename forms, the function as a block or anything that answers `call` (rule 12), and its Channel form waits for story 7; its Lövetest test compares the window with what Lövetest's own `love.draw` shows, so it waits for a port of that screen.
    3. **Textures, canvases, and readback**, 10 tests: `Canvas`, `Image`, `newCanvas`, `newImage`, `newArrayImage`, `newCubeImage`, `newVolumeImage`, `drawLayer`, `setCanvas`, and `draw`. They bind texture settings (mipmaps, formats, readable, depth and stencil), the Texture methods for filters, wrapping, mipmaps, and pixels, `readbackTexture`'s slice, mipmap, and rectangle, `setCanvas`'s forms with several targets and options, and `draw` with a Transform. Rule 10 settles the table form of `setCanvas` as keywords, `set_canvas(canvas, stencil: true)` and `set_canvas([a, b], depth: true)`, with `canvas=` kept for the plain form, so slice 1's `setStencilState` is translated with this slice. All ten are translated, `Canvas` but for its two checks that draw with a shader, which wait for slice 5, along with `ArrayImage`, `CubeImage`, and `VolumeImage` as modules whose `===` asks a texture's type, as rule 2 makes `Canvas`. Rule 10 also gives each target of the table of tables its options as `[texture, layer: 2, mipmap: 1]`, and rule 4 makes `getCanvas` return an Array on every path, `[]`, the canvases, or one Array of the targets, so slice 1's `canvas` changed with it.
    4. **Fonts and text**, 4 tests: `Font`, `Text`, `newTextBatch`, and `newImageFont`. Font's metrics and fallbacks came first, for the game that sets the order above, with `Font`'s test but for its check of fallbacks, which draws with `newImageFont`; this slice binds image fonts and TextBatch, and finishes that test. All four are translated. `newImageFont` is `ImageFont.new`, a module that returns a `Font` (rule 2), whose `===` is true of every `Font`; `newFont` also makes a BMFont from its definition and images; `print` and `printf` take a Transform; and TextBatch is bound whole. `newText`, LÖVE 11's name for `newTextBatch`, is `Text.new`, which prints LÖVE's deprecation notice; `newFont` from a `Rasterizer` waits for the `love.font` module's Rasterizer.
    5. **Shaders**, 6 tests: `Shader`, `newShader`, `validateShader`, `setShader`, `getShader`, and `setFrontFaceWinding`. They bind Shader, its uniforms through `send` and `sendColor`, and `ImageData.new`, which `setFrontFaceWinding`'s shader draws from. All six are translated, with `Canvas`'s two checks that draw with a shader. `ImageData.new` was already bound, so the slice binds `newShader` and `validateShader`, ported to Ruby where `w_getShaderSource` reads its sources and options and where `_transformGLSLErrorMessages` rewrites a compile error, with the options as keywords (rule 10) and `validateShader`'s results an Array (rule 4); `setShader` as `shader=`, which `nil` resets; and Shader's `send` and `sendColor` for every uniform type but buffers, whose `Buffer` waits for slice 6, as do `newComputeShader`, which nothing can dispatch until then, and `getBufferFormat`, whose records are `Buffer:getFormat`'s. Rule 13 names `Shader:send` `send`, which overrides Ruby's own `Object#send` on a Shader and which RuboCop's `Style/Send` reads as Ruby's, so Lota's own tests call it through `__send__(:send, ...)` until the maintainer settles the collision.
    6. **Meshes, buffers, and particles**, 7 tests: `Buffer`, `ShaderStorageBuffer`, `Mesh`, `newMesh`, `drawInstanced`, `ParticleSystem`, and `newParticleSystem`. They bind Buffer and its formats, Mesh and its vertex attributes, instanced drawing, and ParticleSystem, on the textures and shaders the slices before them bind.

    Lövetest's `Video` and `newVideo` tests belong to story 6, which brings Theora.
2. **Window, keyboard, timer, system, event, and love.** Their 75 tests: text input and key repeat, the remaining window modes and displays, the timer's sleep and averages, the clipboard and power state, the rest of the event queue, and `love.getVersion` and its kin. All 75 are translated and pass. `love.window` came first: all 37 of its tests are translated, two of them skipped as Lövetest skips them (`requestAttention` and `showMessageBox`, which cannot tell that they worked), and seven skipped on a GitHub runner on Linux, as Lövetest skips them. Every function of `wrap_Window.cpp` is bound but `showFileDialog`, whose callback SDL answers from a dialog that nothing in the test harness can answer yet, and `getPointer`, a raw window handle for which Lota has no Ruby type to propose. The rest of the story followed: keyboard (all 10 tests, and every function of `wrap_Keyboard.cpp`, with `isDown` and `isScancodeDown` also reading LÖVE's table of keys as one Array), timer (6, every function), system (10, two skipped as Lövetest skips them, every function of `wrap_System.cpp`), event (6, two skipped as Lövetest skips them, every function of `wrap_Event.cpp` but `_setDefaultModalDrawCallback`), and love (6: `Lota.version`, `version_compatible?`, `deprecation_output=` and `deprecation_output?`, with `errhand` and `run` checked as defined; the `_version` fields are `Lota._version` and its kin by rule 13). `Lota::Event.wait` is marked deprecated as LÖVE marks it, `restart` pushes LÖVE's quit message with `"restart"` for its first argument (Lota ends the game as a quit does, since it does not restart games yet), and `modal_draw_callback=` keeps any object that answers `call` and calls it from the event module's modal draw, its results and errors passing out of the next `pump`; the test extension reaches that draw by asking SDL to run a function on its main thread inside the next pump, as the system's live resize would. The generator learned to call a static method on its class, as clang-tidy asks (`Timer::getTime`), and to read each argument LÖVE checks into a local where LÖVE reads it, since C++ leaves the order of a call's arguments unspecified and GCC named a different missing argument than LÖVE. Left out: `love.event._setDefaultModalDrawCallback`, the hook `boot.lua` calls with the game's frame so that a window being resized keeps drawing on macOS and Windows, which waits for the maintainer to decide whether Lota's loop redraws during a live resize; `love.markDeprecated`, which is `Lota::Deprecation.mark` for Lota's own code; and LÖVE's boot-time `_set*` functions, which `Lota::Boot` binds by hand.
3. **Math, data, image, and font.** Their 44 tests: transforms, Bézier curves, triangulation, compression and hashing, encoding images, and rasterizers and glyph data. Lövetest's `ImageData` test came first, for the game that sets the order above, with `ImageData:encode`, `paste`, and the start of `love.filesystem.openFile`'s File, whose other methods wait for story 4.
4. **The rest of audio and filesystem.** Their 66 tests: queueable sources, effects, recording, positional audio, and the filesystem's mounting, files opened for writing, and directory listing. Audio from memory and positional audio came first, for the game that sets the order above: `Source.new` of a `FileData`, a `Decoder`, or a `SoundData`, Source's place in space, its distances, rolloff, cone, and units of time, and the listener's position, orientation, velocity, Doppler scale, and distance model, with ten of audio's tests and `Source`'s but for its queueable source, filter, and effect.
5. **Joystick, touch, and sensor.** Their 13 tests, run as LÖVE's own CI runs them, with no hardware attached, plus the gamepad mapping database.
6. **Video.** Lövetest's two video tests. Theora is a new library in the gem, so it is licensed under REUSE as every other library is.
7. **Threads.** The Ractor counterpart of `love.thread` and its channels, which ADR 001, section 6, leaves to this point. It is a design question for the maintainer first, then Lövetest's five thread tests.
8. **flash-blip.** The fixture Plan 001 held back: shaders, canvases, generated audio, `love.thread`, and HTTP through `Net::HTTP` where it uses LuaSocket. It is also the heaviest binding load of any fixture, at 1,300 to 2,600 calls a frame, so it tests ADR 001, section 8's decision to keep Rice.
9. **`lota fuse`.** ADR 002: a prebuilt runtime per platform, Ruby from rv-ruby on macOS and Linux, and a game written into it the way LÖVE fuses one, signed on macOS. Fused games save where LÖVE's fused games save (ADR 003, section 8). Windows follows ADR 002, section 4's spike.

Plan 001's platform stories (Windows, Intel Macs, and phones and tablets) continue alongside these, and each new module lands on every platform that has a gem.

## Where the work stands

Story 1's slices 1 to 5 are done, and so is everything the game that sets the order asked for first, and so is all of story 2 (`love.window`, keyboard, timer, system, event, and love). The next request is shipping a game; slice 6 (meshes, buffers, and particles) keeps its place in the plan. Story 9, `lota fuse`, waits for the maintainer's decision about Fledge (github.com/setdef/Fledge), which builds per-platform Ruby runtimes and app bundles, so `lota fuse` may become a thin wrapper over it, a decision that may change ADR 002.

Two failures on Linux CI are known and left for later. `RenderTargetTest#test_readback_reads_into_an_image_data_given` reads zeros from a canvas read back into an ImageData under Mesa, and Lövetest run through `lota run` makes 64,873 assertions on Linux where the test expects macOS's 64,871, so some translated test asserts twice more there. The sanitized suite fails with them. macOS is green.

The gate runs its checks in parallel lanes (`tasks/gate.rake`), reuses the reference love's runs while nothing they read changes (`test/parity/reference_cache.rb`), and takes about seven minutes clean and two warm on the maintainer's machine. Tests that take the pointer or keyboard focus hold the desktop input lock (`tasks/desktop_input.rb`), a protocol shared with another of the maintainer's projects and meant to become a small shared gem; on macOS it says and shows when a person should step away. A person steps away while those tests run, and the tests never imitate or block a person's mouse.

## Open questions

- **`showMessageBox`'s buttons form, and `showFileDialog` and `getPointer`.** `show_message_box` reads the table's `enterbutton` and `escapebutton` as keywords, as rule 10 gives it. What rules 4 and 10 do not settle is how it tells LÖVE's two forms apart, which it does by whether the third argument is an Array; the maintainer confirms or changes that. `show_file_dialog` waits for a way to answer SDL's file dialog in tests, and `pointer` for a decision about what Ruby holds a raw window handle as.
- **`v_sync`.** Rule 13 names `getVSync` `v_sync`, as the name table already did, while `set_mode(vsync:)` and `Mode#vsync` keep LÖVE's field name. The maintainer decides whether the rule should treat VSync as one word, as it does DPI.
- **RuboCop's Style/Send.** `Shader#send` keeps LÖVE's name, so Lota's own tests call it through `__send__` while the repository enables Style/Send, which RuboCop leaves off by default. The maintainer decides whether to turn it off.
- **The deprecation prefix.** LÖVE prints `LOVE - Warning:` and Lota prints `Lota - Warning:`, following the trademark rule. The maintainer has not confirmed it.
- **`Lota::Window::DisplayMode`.** `fullscreen_modes` returns frozen records (rule 10), but LÖVE gives these tables no name, so the class name is Lota's. Lota's other records take the name of the getter that returns them (`Mode` for `getMode`, `Info` for `getInfo`, `Stats` for `getStats`), which would make this one `FullscreenMode`; `DisplayMode` follows SDL's `SDL_DisplayMode` instead. Recommendation: rename it `FullscreenMode`, so one rule names every record.
- **`Lota::Info`.** LÖVE puts `getVersion`, `isVersionCompatible`, the deprecation switches, and the `_version` fields on `love` itself, so they are methods of `Lota` (rule 1). Lota defines them in a public module, `Lota::Info`, and extends `Lota` with it, which gives the API a name LÖVE does not have: a game sees it among `Lota`'s ancestors and in the docs. Recommendation: keep it, as `Lota::DefaultCallbacks` already holds the default callbacks, since one module documents these methods in one place.
- **Restarting.** `Lota::Event.restart` queues LÖVE's quit message with `"restart"` first. LÖVE's `love.run` then returns `"restart"`, and `love.cpp` starts the game over: it drops the Lua state and initializes the engine's modules again, with the restart's first argument as `love.restart`. `lota run` exits with 0 instead. Ruby can reload code in a running process, as Rails does with Zeitwerk, but only the constants it autoloaded by name, with the interpreter, the gems, and every global change left as they are. A game's plain `require`s, its `def Lota.update` methods on a shared module, its patches to core classes, and the engine's window and modules fall outside that, and Lota does not yet define what an in-process restart would reset. How a game restarts is the maintainer's to decide. Recommendation: `lota run` starts itself again with `exec` and the same arguments, passing the value on as `Lota.restart`, which gives the whole fresh start LÖVE gives without tracking what a game changed. A spike on 2026-11-02 tried `Ruby::Box` (Ruby 4.0.7). A game runs correctly in one, and the cost of `RUBY_BOX=1` on Lota's binding calls is within noise. A restart by dropping the box does not work, because Ruby never frees a box that defines a named class or module, and every Lota box defines `Lota`: five restarts left five engine copies, their audio devices and threads, and about 36 MB each. Each box also gets its own copy of the native extension, loaded from a temporary directory, which breaks the extension's `@loader_path` rpaths unless `TMPDIR` is pointed at its directory; the variable must be set as the process starts; and `$stdout` redirection breaks under it. A box cannot keep the window across a reload either. Lota also never releases its engine modules, as LÖVE's `lua_close` does at the end of a restart, which an in-process restart would need and `exec` makes unnecessary. Revisit boxes when a Ruby release frees them.
- **Tables in messages.** LÖVE carries a Lua table through `push`, `restart`, and a modal draw callback's results, and gives it back as a table. Ruby's counterparts are Hash and Array, but a table comes back with its keys as LÖVE stores them, every number a double, so `[2]` would return as `{1.0 => 2.0}`. Lota refuses tables for now. Recommendation: give back an Array when a table's keys are 1 to n, as a Lua sequence's are, and a Hash otherwise.
- **A parameter's name in a message.** ADR 001, section 7, rewrites the module and function names in LÖVE's messages and leaves the rest word for word, so `Lota::Event.wait`'s notice reads "replaced by waitTimeout parameter in Lota::Event.pump", naming a parameter Lota calls `wait_timeout`. An earlier commit wrote `wait_timeout`, which the rule does not allow, so Lota follows the rule again. The maintainer decides whether the rule should also rename parameters, by rule 13.
- **Docker.** The local Linux image, `lota-linux-dev`, starts again now that the disk has room, and reproduces CI's Linux failures. Its compiler runs out of memory at the default parallelism, so build with `CMAKE_BUILD_PARALLEL_LEVEL=2`.
