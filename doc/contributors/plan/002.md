# Plan 002: Bind the Rest of LÖVE, Then Ship Games

ADR 001, section 1, binds the whole engine. Plan 001 bound only what its five stories needed: about 325 of the roughly 1,100 functions and methods in the binding generator's name table, and about 100 of Lövetest's roughly 360 tests. A game that calls anything else stops with a `NoMethodError`, however well the rest of Lota matches LÖVE. This plan binds the rest, then lets a developer ship what they build.

Plan 001's way of working still holds: vertical slices, each done when code someone else wrote behaves in Lota as it does in LÖVE, through the same gate, on every platform with a gem.

## What done means

Every one of Lövetest's tests (`vendor/love/testing/tests`), translated by ADR 001's rules, passes in Lota and from the installed gem, on every platform Lota ships a gem for, against the expected images LÖVE's own CI compares with. Where Lövetest skips a test on a platform, Lota skips it there too, for the same reason. Lövetest counts as the acceptance test for each module, and published games stay the acceptance test for behavior over time.

## How bindings are written

The generator writes every binding it can, and each story extends it before binding by hand. A binding that stays hand-written records why in `ext/lota/bindings.rb`, as now. A measurement on 2026-10-28 found that moving the wrap logic into Ruby over directly bound engine methods would remove only about 40 to 55 percent of the C++. It would cost nothing per call only if every binding were written with care, and Rice's enum values would stop being shareable between Ractors. So bindings stay in C++, and each story first teaches the generator the hand-written patterns it meets, of which about 80 of the 138 reduce to plain bindings.

The first such step moved 27 of them. The generator now returns the engine object a wrap function pushes, and gives Ruby the reference of one it made and released; returns nil where a function pushes nil or returns nothing; makes the checks of LÖVE's guard helpers, such as `luax_checkgraphicscreated`, where they are called; reads a count of the arguments as whether one is given; and types the declarations, C arrays, and numbers it could not before. Several of the 80 turned out not to reduce: the joint constructors that choose their form by `lua_gettop` and `Body:applyForce` read one position as a number or a boolean, and `lua_gettop` counts an argument given as nil, which Rice passes as none, so they keep their Array of arguments until the generator can write one. The error messages' name table went to Ruby in the same session: `Lota::ErrorMessage` rewrites a message as Ruby raises it, from a table the generator writes as a frozen Hash.

## Stories

The order follows what games call most. Each story's Lövetest module is its acceptance test.

A real game now sets the order ahead of story 1's remaining slices. A downstream game runs on Lota, and what it calls comes first: (1) finish slice 2; (2) Font's metrics, and the fix that makes `t.window.highdpi` work as it still does in LÖVE 12; (3) `ImageData#encode` and `capture_screenshot`, so a game can save a frame; (4) slice 3's mipmaps, filters, and stencils; and (5) audio from memory and positional audio. Then the order below resumes. Each item still lands with the Lövetest tests it covers.

## Two ends of shipping a game

LÖVE serves a newcomer and a studio, and Lota must too. A newcomer needs no command line: on desktop a game folder dropped onto the player becomes an app (Fledge's draft design for `fledge build --from`), and on Android a prebuilt player opens a game folder, as LÖVE's does; Apple permits no generic player on iOS, so there LÖVE and Lota both hand over an Xcode project, which the iPad kit does. A studio, which ships a game like Balatro as an app of its own, needs the project itself: an Xcode and an Android project it opens, brands, signs with its own keys, and builds from source, so that it can audit and reproduce the build and keep its licences in order. So prebuilt engine binaries per target are the default, built in Lota's CI and fetched by checksum, and building from source stays supported beside them. Every story that touches shipping answers both: what a newcomer does without a terminal, and what a studio gets to own.

A phone links what its desktop counterpart's bundle links, measured in the gems' manifests (iOS as macOS, without Vulkan; Android as Linux); no phone's link map is read yet.
- **Store listings.** Settled for iOS: the privacy manifest. `fledge build ios` writes `PrivacyInfo.xcprivacy` with the two categories Lota's engine and SDL touch, and `doc/guide/phones.md` says what changes the list. Settled for the macOS app: the hardened runtime and its two entitlements, YJIT included (ADR 002, Consequences). Answered for the macOS App Sandbox, signed ad hoc: Fuse run 42563224537 of the throwaway branch `experiment/fuse-sandbox`, on 2026-11-09, signed a fused windowless game again with `com.apple.security.app-sandbox`, with and without each JIT entitlement and `disable-library-validation`, and on macOS 15.8.2 and 26.7.2 every variant ran in its container (the real home folder refused with `EPERM`), with YJIT on and entering machine code, saved and read back its file, and played through CoreAudio, with the sandbox entitlement alone. YJIT needs neither `allow-jit` nor `allow-unsigned-executable-memory` there; Ruby 4.0.9 reserves its code with `mmap` and no `MAP_JIT` and flips it with `mprotect` (`jit.c`, lines 636 to 748). A sandboxed game saves in its container, `~/Library/Containers/IDENTIFIER/Data/Library/Application Support/<identity>`, because LÖVE asks `NSFileManager` for Application Support (`src/common/apple.mm`, lines 43 to 62), so it saves where a sandboxed LÖVE game would, but not where the same game unsandboxed does. A restart breaks it on macOS 15: the `exec` of the launcher (`Lota::Restart`) dies with `SIGTRAP` in `libsystem_secinit` (`SYSCALL_SET_USERLAND_PROFILE`, in run 42560611676 too), as the new image asks for a sandbox the process already has; on macOS 26 it restarts. Fledge signs with one fixed entitlements file (`lib/fledge/mac_signing.rb`, `ENTITLEMENTS`) and builds no Mac App Store package, so a sandboxed build is signed again by hand. Not yet tried: a Developer ID or Apple Distribution signature, notarization or App Review with the sandbox, and a game that draws. Still open: whether `lota fuse` offers the sandbox, and what a restart does under it on macOS 15 (see the maintainer's decisions); and MSIX for the Windows Store, which is Fledge's installer side.

- **The rest of Lövetest.** All five of image's tests are translated, now that compressed images are bound. Video's tests are translated, with Theora (story 6). Data's `hash` test is translated, with `Lota::Data.hash` (story 3).
- **Decisions that are the maintainer's.** Whether `lota fuse` stays (see Open questions); whether `lota fuse` offers the macOS App Sandbox, and whether a restart under it on macOS 15, where `exec` kills a sandboxed process, is left as it is, documented, or done another way; how a game is laid out and started on a phone, and whether `lota fuse` builds for phones; the iOS host's two deviations from LÖVE (the status bar is hidden by `Info.plist`; the accelerometer is not presented as a joystick); whether stencil, depth, and MSAA at a non-integer display scale are documented or patched (LÖVE's Metal backend sizes them from the truncated unit width, so the last pixel columns of a landscape iPhone mini are never drawn, `doc/contributors/upstream/011.md`); a pointer to commercial licensing in the README and the notices file; and whether `Lota::Mouse.global_position` keeps LÖVE's answer, which leaks the display list on every call and misplaces the pointer on a third display or after one whose origin is not the desktop's (`doc/contributors/upstream/022.md`), or works around both.
- **Settled.** Lota matches LÖVE and does not add a renderer fallback: a game that may run where Vulkan has no usable GPU excludes it with `t.graphics.excluderenderers`. Text input starts off, as in LÖVE 12. A patch to LÖVE is kept only where a developer has no way to avoid the problem and upstream would be the place for a fix (`physics.patch`, `mesh.patch`, `vulkan_present.patch`, `lz4.patch`). `lota fuse` restarts a fused game as LÖVE does, and passes Fledge's signing options on. Factories that make several objects stay methods (ADR 001, rule 17), and `Fixture ===` is true of every Shape. A raw pointer is a `Fiddle::Pointer` to the same address, and fiddle stays optional, in the game's Gemfile, since Fledge's iOS runtime leaves it out (see Open questions). Two cases the maintainer settled by fidelity to LÖVE on 2026-11-08: `File#open`'s block form is LÖVE's `if file:open("r") then ... file:close() end`, since `File:open` never raises but returns `true`, `false` for a file already open, or `nil` and a message (`wrap_File.cpp:75-94`, `physfs/File.cpp:96-117`), so the block runs only when the file opens, the file closes after it, and the block's value comes back, and otherwise `open` returns what it returns without a block (ADR 001, section 7). `love.filesystem.load` reads Ruby through LÖVE's filesystem, raises `SyntaxError` with LÖVE's "Syntax error: " message at once, and returns a Proc that runs the code at the top level (`wrap_Filesystem.cpp:746-800`), with its arguments as `ARGV` for the call, as a Lua chunk's are its `...`; Ruby has no other place for them, so the Proc swaps the process's `ARGV` and puts it back. Its modes stay LÖVE's: `:t` and `:bt` load Ruby, and `:b` refuses it, after the read, with LuaJIT's message for a text chunk in binary mode.

## Settled in review, 2026-11-02

Rules and parity settle these, so they are decisions, not questions.

- **Names.** `getVSync` is `vsync`: the V of VSync is the first letter of "vertical", which makes it acronym-like, and rule 13 treats an acronym as one word, so the getter agrees with `vsync` in `set_mode` and the settings (ADR 003, section 5). `fullscreen_modes` returns `FullscreenMode`, as the other records take the name of the getter that returns them. `Lota::Info` holds `Lota`'s version and deprecation methods, as `DefaultCallbacks` holds the default callbacks. `Shader#send` keeps LÖVE's name, and Lota's tests call it through `__send__`. Deprecation notices begin `Lota - Warning:`, which follows AGENTS.md's trademark rule.
- **`show_message_box`.** LÖVE tells its two forms apart by the type of the third argument, and Lota does the same: an Array of button names, or a Symbol type. The table's `enterbutton` and `escapebutton` are keywords (rule 10).
- **Deprecation notices keep LÖVE's parameter names.** ADR 001, section 7, rewrites module and function names in a message and keeps the rest word for word, so `Lota::Event.wait`'s notice says `waitTimeout`.
- **Tables in messages.** `push`, `restart`, and a modal draw callback's results carry a table, as LÖVE's do (`lib/lota/event.rb`, through `Lota::Variant`). A table with the keys 1 to n comes back as an Array, and any other as a Hash.
- **Restarting.** `Lota::Event.restart` queues LÖVE's quit message with `"restart"` first, and `lota run` starts itself again with `exec` and the same arguments, passing the value on as `Lota.restart`. A spike tried `Ruby::Box` (Ruby 4.0.7). A game runs correctly in one, and the cost of `RUBY_BOX=1` on Lota's binding calls is within noise. A restart by dropping the box does not work, because Ruby never frees a box that defines a named class or module, and every Lota box defines `Lota`: five restarts left five engine copies, their audio devices and threads, and about 36 MB each. Each box also gets its own copy of the native extension, loaded from a temporary directory, which breaks the extension's `@loader_path` rpaths unless `TMPDIR` is pointed at its directory; the variable must be set as the process starts; and `$stdout` redirection breaks under it. A box cannot keep the window across a reload either. Lota also never releases its engine modules, as LÖVE's `lua_close` does at the end of a restart, which an in-process restart would need and `exec` makes unnecessary. Revisit boxes when a Ruby release frees them.
- **Restart in a fused game, settled by the maintainer on 2026-11-07.** Lota is a faithful port of LÖVE, and LÖVE restarts a fused game as it restarts any other: love.run returns `"restart"`, and love.cpp's `main` runs `runlove` again in the same program with the same `argc` and `argv` and the value as `love.restart` (`src/love.cpp`, `runlove` and `main`), so the game is fused again because the program is. So Lota restarts in every case LÖVE does. The entry script `lota fuse` writes boots the game as ADR 002 says, `exit Lota::Boot.new(game_dir, ARGV, fused: true).call`; `Boot#call` remembers a fused game's arguments and asks for the restart, and a restart runs the program the process runs again, with the same arguments: Fledge's launcher, which runs Ruby inside its own process and so is what LÖVE's `getExecutablePath` names on every platform (`NSBundle.mainBundle.executablePath` in the `.app`, `/proc/self/exe` on Linux, `GetModuleFileNameW` giving `NAME.exe` on Windows), which sets the app up as it first did. Lota does not rely on `exec RbConfig.ruby, $0, *ARGV`, though since Fledge 0.3.0 its `bin/ruby` hands that command to the launcher on macOS and Linux (Fledge's ADR 026, section 3, `runtime/launcher/relaunch.c`), because on Windows `RbConfig.ruby` is still the console Ruby, and running the launcher is the one way that holds on all three; it falls back to Ruby and the script only when the program is Ruby's own, as when someone runs the entry script with `ruby`. Fledge needs no change. The Fuse workflow's `test/games/fuse` restarts once on every platform. `lota run` under `bundle exec` restarts too: it remembers `$0`, which Bundler sets to the program it loads, where `Process.argv0` was `bundle`. A phone still cannot restart by `exec`, as the open phone question says.
- **Touch, joystick, and sensor.** A touch id is an Integer, because LÖVE holds it as a whole number (rule 14). `love.sensor.getName` is `Lota::Sensor.name`, and that name with no argument is still `Module#name`. A touch iOS cancels never reaches `touchreleased`, because LÖVE's `Event::convert` has no case for `SDL_EVENT_FINGER_CANCELED` (`doc/contributors/upstream/006.md`); Lota matches LÖVE, as precedence 2 asks, a test pins it, and a game that needs to know handles it, as a game that reacts only to `touchpressed` does.
- **iOS follows LÖVE's iOS build.** Audio uses Apple's OpenAL framework, as LÖVE's does, so no LGPL code is linked on iOS, and Lota adds `LOVE_SUPPORT_COREAUDIO` and `CoreAudioDecoder.cpp`, which LÖVE's Xcode build compiles, when the iOS build next changes. Each iOS library's licence entry is read file by file, as the desktop ones were.
- **`lota fuse`'s command line is Lota's, so the orchestrator decides it, and keeps it small.** The flags are `--out`, `--identifier`, `--icon`, `--app-version`, and `--sign`: Fledge requires an identifier for a windowed app and an icon is a file, `--sign` is ADR 002's, `--out` keeps a build out of the game's folder, and `--app-version` stays because ADR 002 forbids `t.version` as the app's version and nothing else names it. No other flag is added until a game needs one. `--exclude` followed, and then `--sign-command` and `--notarize`, which the maintainer approved on 2026-11-08 as pass-throughs of Fledge's own signing options, so that a game signed in a cloud service on Windows or notarized on macOS needs no build outside `lota fuse`.
- **Threads, from Ruby's source (master, 2026-10-24; 4.1 is in preview).** `Lota::Thread` and `Lota::Thread::Channel` are built on Ractors (ADR 001, section 6). The API settled in 4.0 (`Ractor::Port`, `#value`, `Ractor.select`; `#take` and `Ractor.yield` are gone), and 4.1's changes are additive: `timeout:` on `receive` and `select`, `Ractor#alive?`, `#value` callable once, class ownership (a non-main Ractor cannot reopen a core class or a required library's class). The "experimental" warning is still printed on first use and has a category, so Lota turns it off with `Warning[:experimental] = false` where it starts a thread. For the native layer: an extension is callable from a non-main Ractor only if `Init_` calls `rb_ext_ractor_safe(true)` before it defines methods, else `Ractor::UnsafeError`; it must guard its own global state, an engine object crosses Ractors only when its type is `RUBY_TYPED_FROZEN_SHAREABLE` and frozen (a `T_DATA` can be neither copied nor moved), `rb_gc_register_address` is per-Ractor so static VALUEs are registered from the main Ractor, and `RUBY_TYPED_THREAD_SAFE_FREE` is set where `dfree` is thread-safe. `require` in a non-main Ractor runs on the main Ractor, so a thread can load a script by name, and the main Ractor must reach an interrupt check, which Lota's frame loop does. Not known: whether an `ObjectSpace::WeakMap`, which Lota's wrapper identity uses, works across Ractors, so each Ractor keeps its own map. Not verified: how `rb_thread_call_without_gvl` interacts with other Ractors. Ractors still receive fixes for crashes and garbage-collector races, so the sanitizer builds and deterministic tests stand guard.

- **Pairs.** A Mesh's `attach_attribute` and `detach_attribute` follow `mount` and `unmount`: a pair with no block form until a game needs one. A ParticleSystem's `start`, `stop`, and `pause` follow a Source's `play` and `stop`: not a pair, since they run across frames.
- **Setters whose first value is an Array or a Data.** `Buffer:setArrayData`, `Mesh:setVertices`, and `Mesh:setVertexMap` are the methods `set_array_data`, `set_vertices`, and `set_vertex_map`, with LÖVE's argument order, because a writer cannot tell such a value from a list of several (rule 6). The setters that take the index first, `Mesh:setVertex` and `setVertexAttribute`, are the writers `vertex=` and `vertex_attribute=`, as `ImageData:setPixel` is `pixel=`.
