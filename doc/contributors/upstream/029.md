# `love.filesystem.setSource` leaves the source empty when it falls back to `StripSuffixIo`

At the pinned LÖVE commit, `b7daef0f7`. `love2d/love`'s `main` has the same code, with the same line numbers in this function. Written as the report we would file; LÖVE accepts none made with generative AI (AGENTS.md, "Reporting upstream"), so it stays here.

A fused game whose executable has data after its zip, such as an Authenticode signature, runs. But `love.filesystem.getSource()` answers `""` and `love.filesystem.getSourceBaseDirectory()` answers `""`, where the same game unsigned answers the executable's path and its folder.

## What happens

`Filesystem::setSource` (`src/modules/filesystem/physfs/Filesystem.cpp`, lines 259-350) mounts the executable with `PHYSFS_mount`. When that fails, as it does for a zip with data after it, it falls back to `StripSuffixIo` (lines 323-344), which finds the zip's end of central directory record and mounts only the zip. That branch ends with `return true;` (line 343). The code that records the source, `gameSource = new_search_path;` (line 347), is after it, so the branch never runs it. Every other successful return in the function sets `gameSource` first (lines 282, 297, 309, 347).

`gameSource` stays empty, and the function's own guard, `if (!gameSource.empty())` (line 265), lets `setSource` run again. What reads `gameSource` then answers as if there were no source:

- `getSource` (line 354) returns `""`.
- `getSourceBaseDirectory` (lines 785-807) returns `""` at its `source_len == 0` check, so a fused game cannot mount its own folder, which `mount` allows (line 391) only when the base directory equals the archive.
- `mount` (line 411) refuses a file inside the game source with `realPath.find(gameSource) == 0`. With an empty `gameSource`, `find` returns 0 for every path, so `mount` refuses every archive that is neither an allowed path nor the source's base directory. We read this and did not run it.

What does not change: `boot.lua` (lines 77-90) takes `pcall(love.filesystem.setSource, exepath)` succeeding as a fused game, so `isFused` is true, and the zip is mounted, so `require` and `love.filesystem.read` find the game's files. The save identity comes from the executable's name (`boot.lua`, the `else` branch after line 123), not from `gameSource`.

LÖVE 11.5's changelog says it "fixed running fused games on Windows when the executable has been code-signed". The fix made the game run; the source it reports was not set.

## To reproduce

On Linux, with a `love` built from `vendor/love` (`bundle exec rake reference:love`), and a game folder holding a `main.lua` and a `conf.lua` that turns off the window, graphics, audio, and sound modules:

```sh
(cd game && zip -qr ../game.love .)
cat love game.love > fused_plain
cat love game.love > fused_signed
head -c 300000 /dev/urandom >> fused_signed
chmod +x fused_plain fused_signed
```

`main.lua` prints `love.filesystem.isFused()`, `getSource()`, and `getSourceBaseDirectory()`. We ran both executables on 2026-11-13:

```
fused_plain:   fused true, source[/tmp/tmp.gzzahOmVsn/fused_plain], base[/tmp/tmp.gzzahOmVsn]
fused_signed:  fused true, source[],                                base[]
```

Random bytes stand in for a signature: `PHYSFS_mount` fails on both, and `StripSuffixIo` finds the record.

## A fix

Set `gameSource = new_search_path;` before `return true;` in the `StripSuffixIo` branch, or let the branch fall through to line 347 after a successful `PHYSFS_mountIo`.

## What Lota does

Nothing, because Lota does not reach the branch. `Lota::Boot#open_filesystem` (`lib/lota/boot.rb`) calls `setSource` with the game's folder, never with an executable that carries a zip, and `PHYSFS_mount` succeeds on a folder, so the fallback does not run. A game fused by Lota is a folder in an application, not a zip appended to an executable. If Lota ever mounts a zip with data after it, it would pass `setSource` the zip's path and check `Lota::Filesystem.source` first.
