# On Android, a game on Vulkan crashes when it leaves the screen

At the pinned LÖVE commit, `b7daef0f7`, with SDL 3.4.10, and in love-android's `main` branch at `1c89bb0b2e` (2026-11-03), which builds LÖVE 12 from a commit 15 commits past `b7daef0f7` with SDL's Java classes of SDL 3. Written as the report we would file; LÖVE accepts none made with generative AI (AGENTS.md, "Reporting upstream"), and SDL asks that generative AI not be used in contributing to it, so it stays here.

A game that LÖVE renders with Vulkan on Android crashes, often but not every time, when its window goes away: when the player presses Home, switches to another app, turns the screen off, or picks an app from a share sheet the game opened. The crash is a SIGSEGV at address 0x98 in the Vulkan loader's `CreateAndroidSurfaceKHR`, under `love.graphics.present`. The same game on OpenGL ES does not crash.

## What happens

The surface goes away on Android's UI thread while the game's thread is in the middle of a frame, and only for an OpenGL window does SDL wait for that frame to end.

1. On Android 7 and newer, `SDLActivity.onPause` does not pause the game. SDL pauses it in `onStop` instead, or in `surfaceDestroyed` if that comes first (`android-project/app/src/main/java/org/libsdl/app/SDLActivity.java`, `onPause`, `onStop`, and `mHasMultiWindow`). Until then the game draws as usual, which is right, since the activity may still be on the screen.
2. `SDLSurface.surfaceDestroyed`, on the UI thread, asks for the pause through `handleNativeState` and then calls `onNativeSurfaceDestroyed` (`SDLSurface.java`, lines 107-116). `nativePause` only queues the pause for the game's thread, which takes it the next time it pumps events (`src/core/android/SDL_android.c`, `nativePause` and `Android_SendLifecycleEvent`, lines 944-1001 and 1561-1567, and `src/video/android/SDL_androidevents.c`, `Android_PumpEvents`, lines 214-239).
3. `onNativeSurfaceDestroyed` (`SDL_android.c`, lines 1307-1344) waits only if the window is an OpenGL one. It retries every 10 milliseconds, up to 50 times, until `backup_done` is set. The game's thread sets that flag when it handles the pause, after it has released its EGL context (`Android_OnPause` and `android_egl_context_backup`, `SDL_androidevents.c`, lines 57-75 and 113-137). For any other window it releases the `ANativeWindow` straight away and sets the window's `native_window` to `NULL`.
4. A Vulkan game's thread is usually inside `love.graphics.present` at that moment, most often waiting there for the next image. `Graphics::present` (`src/modules/graphics/vulkan/Graphics.cpp`, lines 585-683) presents, and then, in `beginFrame` and `beginSwapChainFrame` (lines 1453-1478), acquires the next frame's image. Once the window is gone, either call returns `VK_ERROR_SURFACE_LOST_KHR`. LÖVE asks for a new surface and calls `recreateSwapChain` (lines 3685-3705), and `createSurface` (lines 2070-2076) calls `SDL_Vulkan_CreateSurface`. On Android that passes the window's `native_window`, now `NULL`, as `VkAndroidSurfaceCreateInfoKHR::window` (`src/video/android/SDL_androidvulkan.c`, line 153), and the loader reads through it.

`present` returns at once while graphics is inactive (line 588), and LÖVE's event watch marks graphics inactive on `SDL_EVENT_DID_ENTER_BACKGROUND` (`src/modules/event/sdl/Event.cpp`, lines 83-109). But that event is sent from the game's own pump. The frame that crashes began before the pause reached the pump, so nothing has marked graphics inactive yet. Once the pump has taken the pause, SDL blocks the game in it until the app returns (`SDL_HINT_ANDROID_BLOCK_ON_PAUSE`, on by default), and from then on all is well. On resume, the first present finds the old surface lost and makes a new one from the new window, which works.

## To reproduce

love-android's own debug APK from its CI run 41632391450 (`app-normal-record-debug.apk`, at `1c89bb0b2e`), on a Google APIs x86_64 emulator of API 33 started with `-gpu swiftshader_indirect`, where LÖVE's Vulkan renders. Start it with no game (`adb root`, then `adb shell am start -n org.love2d.android/org.love2d.android.GameActivity`), wait 6 seconds, then press Home (`adb shell input keyevent KEYCODE_HOME`) or turn the screen off (`adb shell input keyevent 26`). Of six tries, three of each, five crashed:

The crash came 32 milliseconds after `surfaceDestroyed`, on SDL's own thread, where LÖVE runs Lua, so it does not depend on which thread runs the game. `doc/contributors/upstream/014.md` found the same crash after a change of configuration. There too the activity's surface was destroyed while the game was drawing.

A OnePlus Nord N30 5G (Android 14, Adreno 619, Vulkan 1.1.128) showed the same with a game built on Lota 0.2.2, whose engine is LÖVE's at `b7daef0f7`. The cycle force-stop, start, 8 seconds, Home, 3 seconds, start, the recent apps, 2 seconds, start crashed it 6 times in 6 on Vulkan and never in 6 on OpenGL ES. Picking Messages from a share sheet crashed it too, 62 milliseconds after `surfaceDestroyed` and `nativePause`. On the API 36 emulator LÖVE finds no Vulkan device it can use, so OpenGL ES renders there and nothing crashes.

## A fix

Make the UI thread wait for the game to pause before the surface goes, for Vulkan as SDL already does for OpenGL. Either SDL or the app's activity can do that. SDL could wait in `onNativeSurfaceDestroyed` for any window, not just an OpenGL one, until the game's thread has taken the pause. An activity can override `createSDLSurface` with a surface whose `surfaceDestroyed` asks for the pause, waits for the game to report it, and then calls SDL's. LÖVE could also make `createSurface` refuse a window with no `native_window` and leave the swap chain alone until the window returns, but that alone would still leave a frame drawing on a window that is being released.

## What Lota does

Lota's Android host and extension do the waiting. On Android, `Lota::Native::Event.open` adds an SDL event watch (`ext/lota/native/event.cpp`, `watch_android_pause`). It runs on the game's thread inside the pump, on the same events and the same main-thread test as LÖVE's watch, and calls the activity's static `gamePaused(boolean)` through JNI. `MainActivity` returns a surface whose `surfaceDestroyed` asks for the pause, as SDL's does, then waits up to 2 seconds for `gamePaused(true)`, and then calls SDL's `surfaceDestroyed` (`ext/lota/phone/host/android/src/main/java/org/setdef/fledge/host/MainActivity.java`, `GameSurface`). It does not wait for a game that has not opened its event module, or that has ended. In practice it waits a few milliseconds: the game's next pump takes the pause, and by then the game is drawing no frame. The behaviour is LÖVE's: the game hears `Lota.visible(false)` and `Lota.visible(true)`, stops while it is away, and draws again when it returns.

It is not a patch to LÖVE's engine, since Lota's own code can do it, and ADR 005 allows a patch only when it cannot. On an emulator of API 33 under Vulkan, Lota's sample game, `test/games/phone`, crashed without it on Home, the screen turned off, and the cycle above (2 of 6). With it, the game came through every one of those, and another app and a share sheet too, 6 cycles in 6. On OpenGL ES, on API 33 and API 36, it came through all of them with and without the change. `.github/phones/android_emulator.sh` sends the game to the background and brings it back, and fails on a crash or if the game draws nothing after it returns. Without the change it failed 3 runs in 3 on the API 33 emulator.

On the OnePlus Nord N30 5G above, a game's build with the change and Vulkan forced came through 6 of 6 cycles of Home and the recent apps. Its surface was destroyed and made again 12 times, with no crash and no wait that ran out. It also came through a share sheet to Messages and back, each in the same process and drawing again, and the screen turned off. Unlocking was not tried, since the phone has a PIN. From `nativePause` to SDL's `surfaceDestroyed`, the wait took about 15 milliseconds.
