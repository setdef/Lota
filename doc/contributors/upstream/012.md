# `BezierCurve:getDerivative` lets the engine's exception escape into Lua

At the pinned LÖVE commit, `b7daef0f7`. Written as the report we would file; LÖVE accepts none made with generative AI (AGENTS.md, "Reporting upstream"), so it stays here.

`BezierCurve::getDerivative` throws `love::Exception("Cannot derive a curve of degree < 1.")` for a curve of one control point (`src/modules/math/BezierCurve.cpp`, lines 97-100). Every other call into the engine that can throw in `wrap_BezierCurve.cpp` runs inside `luax_catchexcept`, which turns the exception into a Lua error with its message (`getControlPoint`, `setControlPoint`, `insertControlPoint`, `removeControlPoint`, `evaluate`, `getSegment`, `render`, and `renderSegment`). `w_BezierCurve_getDerivative` calls it outside one (`src/modules/math/wrap_BezierCurve.cpp`, lines 43-50, at line 46), so the C++ exception unwinds through the Lua C function itself.

What a game sees then is left to how the Lua runtime treats a C++ exception it did not raise, rather than to LÖVE, and is not the Lua error with the message "Cannot derive a curve of degree < 1." that `luax_catchexcept` would raise.

To reproduce: `love.math.newBezierCurve(0, 0):getDerivative()`, inside `pcall`, and print the error.

A fix would wrap the call as its neighbours do: `luax_catchexcept(L, [&]() { deriv = new BezierCurve(curve->getDerivative()); });`.

What Lota does: Lota binds `getDerivative` through the binding generator, and Rice turns every C++ exception into a Ruby one (Lota's translation, `ext/lota/native/errors.hpp`), so `Lota::Math::BezierCurve#derivative` raises RuntimeError with LÖVE's own message, as the wrap function would with `luax_catchexcept`. `test/native/math_functions_test.rb` (`test_the_curves_engine_errors_reach_ruby`) checks it. No patch is needed.
