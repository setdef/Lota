# Text input starts off in LÖVE 12, so a game that never calls `setTextInput` gets no `love.textinput`

At the pinned LÖVE commit, `b7daef0f7`, built with SDL 3.4.10. Written as the report we would file; LÖVE accepts none made with generative AI (AGENTS.md, "Reporting upstream"), so it stays here.

When LÖVE added `love.keyboard.setTextInput`, its commit said text input was "enabled by default" (`389e99bf2`), and so it was on a computer: SDL 2 turned text input on when video started, holding back the on-screen keyboard while it did (SDL 2.30.12, `src/video/SDL_video.c`, lines 580-592, in `SDL_VideoInit`). SDL 3 stopped doing that. Its migration guide says "Text input is no longer automatically enabled when initializing video, you should call SDL_StartTextInput() when you want to receive text input" (SDL 3.4.10, `docs/README-migration.md`, line 1014), its header says "Text input events are not received by default" (`include/SDL3/SDL_keyboard.h`, line 359), and nothing inside SDL calls `SDL_StartTextInput`: a window's `text_input_active` is set only by `SDL_StartTextInputWithProperties` (`src/video/SDL_video.c`, lines 5804-5844). SDL drops typed text for a window whose text input is off (`src/events/SDL_keyboard.c`, `SDL_SendKeyboardText`, line 768, and the editing events at lines 799 and 859), on every platform, since that check is common code.

LÖVE 12 calls `SDL_StartTextInput` only from `Keyboard::setTextInput` (`src/modules/keyboard/sdl/Keyboard.cpp`, lines 136-145); neither the window (`src/modules/window/sdl/Window.cpp`) nor `boot.lua` turns it on. `love.keyboard.hasTextInput` is `SDL_TextInputActive` (lines 167-173), so it is false when the window opens. The SDL 3 port (`dda7603d0`, then `337d8fa04`, which removed SDL 2) carried the calls over without replacing the start that SDL 2 used to make, and `changes.txt` says nothing about the change. The wiki still describes LÖVE 11's default. LÖVE's main branch was the same when this was written.

The result is that a LÖVE 11 game with a name entry, a chat box, or a console, which handles `love.textinput` without ever calling `setTextInput(true)`, runs on LÖVE 12 with `love.keypressed` working and no text arriving, and with no error. Since SDL 3 keeps text input for each window, a game that turns it on and later makes a new window, as `love.window.setMode` does when it changes the renderer (`Window.cpp`, lines 565-566), has it off again.

To reproduce, on a computer: a `main.lua` with `function love.load() print(love.keyboard.hasTextInput()) end` and `function love.textinput(t) print(t) end`. It prints `false`, and typing in the window prints nothing. Adding `love.keyboard.setTextInput(true)` to `love.load` makes it print `true`, and typing prints the text. On macOS, the love that Lota builds from the pinned commit as LÖVE's CI does (`rake reference:love`) printed `false` at load, at the first update, and at the thirtieth, with the window focused, in each of six runs.

A fix would either start text input on each new window, on a computer, to keep LÖVE 11's behavior, or keep SDL 3's default and say so in `changes.txt` and on the wiki, since games written for LÖVE 11 rely on the old one. SDL 3's guide gives a reason for the second: text input can show an input method editor and swallow key presses.

What Lota does: nothing different from LÖVE. `Lota::Keyboard.text_input?` is false when the window opens, as `hasTextInput` is, and a game turns text input on with `Lota::Keyboard.text_input = true`. Lota's documentation of `text_input=` says so, and `test/native/lota_run_test.rb` (`test_callbacks_run_in_loves_order_and_the_game_exits_with_its_status`) holds a game started with `lota run` to it. Turning it on for every game would make a Lota game behave differently from the same game in LÖVE 12, which ADR 001 puts first, so it is the maintainer's to decide.
