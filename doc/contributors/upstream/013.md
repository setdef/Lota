# love.data's functions return a ByteData that Lua sees as a plain Data

At the pinned LÖVE commit, `b7daef0f7`. Written as the report we would file; LÖVE accepts none made with generative AI (AGENTS.md, "Reporting upstream"), so it stays here.

Given the container type `"data"`, `love.data.decompress`, `encode`, `decode`, `hash`, and `pack` make a `ByteData` and push it with `luax_pushtype(L, Data::type, data)` (`src/modules/data/wrap_DataModule.cpp`, lines 191, 238, 287, 345, 374, and 390). `luax_rawnewtype` gives the new userdata the metatable of the type it is passed, not of the object's own (`src/common/runtime.cpp`, lines 623-648), so these objects are a `ByteData` in C++ and a `Data` in Lua: `:type()` returns `"Data"`, `:typeOf("ByteData")` returns false, and `ByteData`'s own methods, `clone`, `setString`, `setFloat`, and the rest, are missing, though `love.data.newByteData` returns a full `ByteData`. `luax_pushtype` reuses an object's userdata once it has one, so `pack` into an existing `ByteData` returns that `ByteData` as it was.

The pushes date from the commit that gave these functions their container type (`9fa73f8b8`, 2017), in which `love.data.compress` pushes its `CompressedData` with `luax_pushtype(L, cdata)`, as its own type.

To reproduce: `print(love.data.decompress("data", love.data.compress("data", "zlib", "hi")):type())` prints `Data`, and `love.data.decode("data", "hex", "6869"):setString("x")` raises "attempt to call method 'setString' (a nil value)".

A fix would push each with `luax_pushtype(L, data)`, as `w_newByteData` does (line 111).

What Lota does: what LÖVE does. LÖVE's root type Data is the class `Lota::Data` (ADR 001, rule 1, and section 7), and these functions return an object of that class itself, whose `object_type` is `"Data"`, which is not a `"ByteData"`, and which has Data's methods and none of ByteData's, as the Lua object has.
