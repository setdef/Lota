# `Mesh` frees its vertex data with `delete`, not `delete[]`

At the pinned LÖVE commit, `b7daef0f7`. Written as the report we would file; LÖVE accepts none made with generative AI (AGENTS.md, "Reporting upstream"), so it stays here.

Both constructors of `love::graphics::Mesh` that keep vertex data of their own allocate it with `new uint8[...]` (`src/modules/graphics/Mesh.cpp`, lines 53 and 92), and `Mesh::~Mesh` frees it with `delete vertexData;` (line 140). Freeing with `delete` what `new[]` allocated is undefined behavior in C++. With glibc and GCC it frees the memory as `delete[]` would, so nothing goes wrong you can see, but AddressSanitizer reports it the first time a `Mesh` is destroyed: `ERROR: AddressSanitizer: alloc-dealloc-mismatch (operator new [] vs operator delete)`, in `love::graphics::Mesh::~Mesh()`. To reproduce, build LÖVE with `-fsanitize=address` on Linux, where ASan checks this by default, and run `love.graphics.newMesh({{0, 0}, {1, 0}, {1, 1}})` and collect the Mesh. macOS's ASan leaves `alloc_dealloc_mismatch` off by default, so it reports nothing there. LÖVE's `main` has the same lines.

The fix is `delete[] vertexData;` at line 140. Nothing outside `Mesh.cpp` can reach the pointer, which is private, or change how the destructor frees it, so Lota compiles `Mesh.cpp` with a patch of that one statement (`ext/lota/engine/mesh.patch`, applied by `ext/lota/engine/CMakeLists.txt`). `test/native/buffer_test.rb` destroys a Mesh in the sanitized run, which ASan ends on Linux without the patch.
