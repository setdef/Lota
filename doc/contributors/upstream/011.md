# At a fractional DPI scale, Metal's backbuffer stencil and MSAA textures are narrower than the drawable

At the pinned LÖVE commit, `b7daef0f7`. Written as the report we would file; LÖVE accepts none made with generative AI (AGENTS.md, "Reporting upstream"), so it stays here.

The window gives the graphics module its size twice: in pixels, as SDL reports the window's pixels, and in units, as those pixels divided by the DPI scale and cut to a whole number, `(int) scaledw` (`src/modules/window/sdl/Window.cpp`, lines 649-656 and 716-718). When the scale does not divide the pixel size evenly, the unit size falls short of the pixel size by a fraction of a unit. Most of the Metal backend is unaffected, because it sizes the viewport and the default scissor from the pixel size (`src/modules/graphics/metal/Graphics.mm`, lines 932-974), the projection spreads the unit size over that viewport (`src/modules/graphics/Graphics.cpp`, lines 2919-2942), and a clear is the load action of the whole attachment (`Graphics.mm`, lines 1559-1600).

The textures the Metal backend makes for the backbuffer are the exception. `Graphics::backbufferChanged` makes the MSAA color texture and the depth and stencil texture from the unit size, with a scale worked out from the height: `ts.width = settings.width` and `ts.dpiScale = pixelHeight / height` (`Graphics.mm`, lines 500-531). `Texture`'s constructor then makes their pixel size `(int) (width * dpiScale + 0.5)` (`src/modules/graphics/Texture.cpp`, lines 232-233), which need not be the drawable's. `useRenderEncoder` attaches that depth and stencil texture to the drawable's render pass (`Graphics.mm`, lines 692-696), and resolves the MSAA texture into the drawable (lines 674-679). A Metal render pass is as large as its smallest attachment. So where the texture comes out narrower than the drawable, the columns past it lie outside the pass, and no clear, draw, or resolve is defined to write them.

The depth buffer and MSAA are sized the same way. The one `Texture::Settings` serves all three textures, the depth and stencil texture being made whenever `stencil` or `depth` is set (lines 518-530), so a window with a depth buffer, or with MSAA, narrows the pass just as a stencil buffer does. A window's stencil buffer is on by default (`src/modules/window/Window.h`, line 290), so a game that changes nothing gets the stencil texture. On an iPhone 13 mini in landscape, SDL reports a drawable of 2338 by 1080 pixels at a scale of about 2.8793, and the units come out 811 by 375. The scale `backbufferChanged` uses is then 1080 / 375 = 2.88, and the stencil texture is (int) (811 × 2.88 + 0.5) = 2336 pixels wide, two short of the drawable. In portrait the same arithmetic gives 1081 by 2338 for units of 375 by 811, or exactly 1080 by 2338 for 375 by 812, so the texture is never narrower and nothing is cut off. At a whole-number scale the sizes always agree, because SDL's pixel size on Apple's platforms is the window's size in points times the scale, so dividing by the scale is exact. Every Mac's backing scale is a whole number, so the fault cannot arise on macOS.

The other backends differ. OpenGL, on every platform, including Android, makes the same internal backbuffer from the unit size (`src/modules/graphics/opengl/Graphics.cpp`, lines 219-243), but only when MSAA is on (lines 213-215). It then blits the backbuffer's full pixel size out of it (lines 1229-1247), so the same columns go uncopied there with MSAA. Without MSAA it draws to the system framebuffer, whose stencil comes with the context. Vulkan makes its depth and MSAA color images at the swap chain's extent, in pixels (`src/modules/graphics/vulkan/Graphics.cpp`, lines 3410-3411 and 3487-3488), so it is unaffected.

What is proven, and how: a standalone Metal program that sets up a render pass as `Graphics.mm` does, with a BGRA8 color attachment of 2338 by 1080, a `Stencil8` (or `Depth32Float_Stencil8`) attachment of 2336 by 1080, a clear load action, and LÖVE's viewport and scissor of 2338 by 1080. Under Metal's API validation (`MTL_DEBUG_LAYER=1`) the encoder rejects LÖVE's own scissor: "(rect.x(0) + rect.width(2338))(2338) must be <= render pass width(2336)". Without validation, an Apple M1 Max under macOS still clears all 2338 columns, which is the undefined behavior happening to come out right. Through LÖVE's own canvases the projection, viewport, and clear write every pixel. A Canvas of 811 by 375 units at a `dpiscale` of 2338 / 811 is 2338 by 1081 pixels, and a blue clear, or a rectangle 811 or 812 units wide, reaches all 2338 columns. That is the screen's case, except for the stencil.

What a Simulator confirms: a game on an iPhone 13 mini Simulator (iOS 26.1) found columns 2336 and 2337 of `love.graphics.captureScreenshot`'s image black after a blue clear, in landscape only, and the Simulator's own capture of the 2340-pixel panel darkening over its last three columns. The screenshot copies the whole drawable (`Graphics.mm`, lines 1697-1716), so the black is in the drawable. With the window's stencil and depth off, and nothing else changed, both turned blue. What is still unconfirmed is a physical phone, on which a thin column of the wrong colour was seen at the right edge in landscape only. The undefined columns predict that column, but nobody has yet looked at a phone with the stencil off.

A fix would make the backbuffer's textures at the drawable's pixel size: set `ts.width` and `ts.height` to `settings.pixelWidth` and `settings.pixelHeight` with `ts.dpiScale = 1`. Nothing samples these textures in units.

What Lota does: nothing different from LÖVE. It runs LÖVE's Metal and OpenGL backends unchanged, and neither its Ruby nor its native layer touches the backbuffer's size, viewport, scissor, clear, or screenshot. Lota keeps LÖVE's default of a stencil buffer, which games use. The maintainer has two options. The first is to document that a game which never draws to the screen's stencil can set `stencil: false` (and leave `depth` false and `msaa` 0), which leaves the drawable as the pass's only attachment. That changes no code, but every such game has to know to do it, and a game that needs the stencil or MSAA keeps the strip. Without a stencil, drawing to the stencil raises LÖVE's error unless a Canvas with one is set (`Graphics.cpp`, lines 748-752). The second is a small patch file to `Graphics.mm`'s `backbufferChanged`, making the two textures at the pixel size as above. That fixes every game, but it carries a change to LÖVE's engine, which ADR 005 allows only when nothing in Lota can do the work. Nothing in Lota can resize those textures, because Lota never sees them.
