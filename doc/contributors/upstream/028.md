# Lövetest's `love.test.thread.Thread` races its own thread

At the pinned LÖVE commit, `b7daef0f7`. Written as the report we would file; LÖVE accepts none made with generative AI (AGENTS.md, "Reporting upstream"), so it stays here.

Lövetest's `love.test.thread.Thread` checks that a thread is running just after it starts. Nothing makes that so. The thread can finish first, and then the test fails. In LÖVE it almost never does, only because a LÖVE thread takes longer to start than the test's thread code takes to run.

## What happens

The test (`testing/tests/thread.lua`, lines 83-109) starts a thread whose Lua adds the numbers from 1 to 100,000, and at once asserts `thread:isRunning()`, "check started" (lines 96-97).

`Thread::start` (`src/modules/thread/sdl/Thread.cpp`, lines 43-70) sets `running` when `SDL_CreateThread` returns. `thread_runner` (lines 91-104) clears it as soon as the thread's function returns. `isRunning` (lines 85-89) reads it. So `isRunning` answers `false` whenever the thread has already finished, however soon after `start` the caller asks.

What keeps the test passing in LÖVE is the thread's startup. `LuaThread::threadFunction` (`src/modules/thread/LuaThread.cpp`, lines 50-115) makes a new Lua state, opens Lua's libraries, and requires `love`, `love.thread`, and `love.filesystem` (lines 55-81) before it loads and runs the thread's code (lines 87-101). That startup usually takes far longer than the main thread needs to reach its next line. If the main thread loses its CPU between `start` and `isRunning` for longer than the whole thread takes, as on a busy machine, the assertion fails.

## To reproduce

The race shows only when the main thread is held up between the two lines. To force it in LÖVE, add a delay that stands for the main thread being descheduled:

```lua
local thread = love.thread.newThread([[
  local b = 0
  for a = 1, 100000 do b = b + a end
]])
thread:start()
love.timer.sleep(0.5) -- the main thread descheduled, as on a busy machine
print(thread:isRunning()) -- false; the test expects true
```

Without the delay, run Lövetest's thread tests repeatedly while other processes keep every core busy.

## A fix

The test could check `isRunning` from inside a thread that waits on a channel until the main thread has checked it, so that the thread cannot end before the check, as its Channel test already waits on channels.

## What Lota does

Lota translates the test as it is (`test/lovetest/tests/thread.rb`, `test_thread`) and adds no delay, retry, or skip to hide the race. A Lota thread runs `threadFunction`'s steps too: its Ractor requires Lota, its thread module, and its filesystem, in the order LÖVE's thread requires `love`, `love.thread`, and `love.filesystem`, before the code runs (`Lota::Thread::Thread::Body.run`). Ruby 4.1 runs each of those requires in the main Ractor, so the thread waits for the main thread before its code starts, but Lota's thread still starts faster than LÖVE's, and Ruby runs the 100,000 additions in a few milliseconds.

On Linux with Ruby 4.1.0-preview1, the translated test, run alone 200 times, never failed, before or after Lota ported those steps: 0 of 200 on an idle machine and 0 of 200 with a busy process on each of its 16 hardware threads, both times. Before the port, it failed twice in full gates, whose lanes load the machine with builds and games as well as CPU, once under `lota run` (`test/native/lota_run_test.rb`, `test_lovetest_passes_when_run_by_lota_run`) and once in `test/lovetest/thread_test.rb`. The maintainer decided on 2026-11-13 to keep the test as LÖVE runs it, with no retry, skip, or delay, unless the race weighs down Lota's tests or CI, wasting reruns of its checks; if it starts costing reruns, the decision is revisited.
