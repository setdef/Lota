# `love.font.newBMFontRasterizer` decides whether to decode each image by its first argument

At the pinned LÖVE commit, `b7daef0f7`. Written as the report we would file; LÖVE accepts none made with generative AI (AGENTS.md, "Reporting upstream"), so it stays here.

`convimagedata(L, idx)` converts the image at `idx` to an `ImageData` through `love.image.newImageData` when it is a file name, a `File`, or a `FileData` (`src/modules/font/wrap_Font.cpp`, lines 152-156). Its test of a file name reads index 1, `lua_type(L, 1) == LUA_TSTRING`, where its other two tests read `idx`. `w_newImageRasterizer` calls it with index 1 (line 202), so the slip changes nothing there. `w_newBMFontRasterizer` calls it for its second argument (line 182) and for each image of a table there (line 172, with `idx` -1), while index 1 is the BMFont's definition, so whether an image is decoded depends on the definition's kind, not the image's:

- With the definition given as a file name, the usual case, every image is passed to `love.image.newImageData`, an `ImageData` too. An `ImageData` is a `Data`, so `newImageData` reads its pixels as the bytes of an image file (`src/modules/image/wrap_Image.cpp`, lines 86-98), which no decoder reads, and the call fails.
- With the definition given as a `FileData`, an image given as a file name is not decoded, and `luax_checktype<image::ImageData>` (lines 173 and 183) raises that an `ImageData` was expected.

`love.graphics.newFont` makes its BMFonts through `newBMFontRasterizer` (`src/modules/graphics/wrap_Graphics.cpp`, lines 1388-1397), so it fails the same way.

To reproduce, with a BMFont `font.fnt` whose one page is `font.png`: `love.font.newBMFontRasterizer("font.fnt", love.image.newImageData("font.png"))` raises the image module's error that it cannot decode the data, and `love.font.newBMFontRasterizer(love.filesystem.newFileData("font.fnt"), "font.png")` raises "bad argument #2 to 'newBMFontRasterizer' (ImageData expected, got string)". Both work once the test reads `lua_type(L, idx)`.

A fix would read `lua_type(L, idx)` in `convimagedata`.

What Lota does: `Lota::Font::BMFontRasterizer.new` and `Lota::Graphics::Font.new` decode each image by its own kind, an `ImageData` as it is and a file name, `File`, or `FileData` through `Lota::Image::ImageData.new`, which is what `convimagedata`'s other two tests do, so every form that works in LÖVE works the same in Lota, and the two above work too.
