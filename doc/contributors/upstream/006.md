# A cancelled touch never ends: `Event::convert` has no case for `SDL_EVENT_FINGER_CANCELED`

At the pinned LÖVE commit, `b7daef0f7`. Written as the report we would file; LÖVE accepts none made with generative AI (AGENTS.md, "Reporting upstream"), so it stays here.

SDL 3 sends `SDL_EVENT_FINGER_CANCELED`, not `SDL_EVENT_FINGER_UP`, when the system takes a touch away from the program: on iOS for each touch `touchesCancelled:withEvent:` reports, as when a system gesture, an alert, or Control Center claims the fingers (SDL 3.4.10, `src/video/uikit/SDL_uikitview.m`), and on macOS for a trackpad touch whose phase is `NSTouchPhaseCancelled` (`src/video/cocoa/SDL_cocoawindow.m`). LÖVE means to treat it as a release: `Event::convert` names `touchreleased` for it (`src/modules/event/sdl/Event.cpp`, line 437), and `love::touch::sdl::Touch::onEvent` removes the touch for it (`src/modules/touch/sdl/Touch.cpp`, lines 88-90). But the `switch` in `Event::convert` that reaches both lists only `SDL_EVENT_FINGER_DOWN`, `SDL_EVENT_FINGER_UP`, and `SDL_EVENT_FINGER_MOTION` (lines 394-396), so a cancelled touch falls to `default` and makes no message. Both lines that test for `SDL_EVENT_FINGER_CANCELED` are unreachable.

The result is a finger that never lifts. `love.touchreleased` is not called for it, and `love.touch.getTouches` lists its id until a later touch with the same id lifts, which on iOS, where SDL's finger id is the `UITouch`'s address, may be never. A game that tracks fingers by id, as a game of tapping things does, keeps the cancelled one held. The mouse events SDL makes of the first finger do not share the gap: SDL releases their left button for any finger event that is not a press, a cancelled one included (`src/events/SDL_touch.c`, `SDL_SendTouch`), so `love.mousereleased` arrives with `istouch` true while `love.touchreleased` does not. A game that reads only the mouse callbacks sees the cancelled touch end; one that reads the touch callbacks does not.

To reproduce without a device, push the events through SDL's queue from a running game (LuaJIT's FFI will do): `SDL_EVENT_FINGER_DOWN` for finger 7, then `SDL_EVENT_FINGER_CANCELED` for finger 7. `love.touchpressed` is called once, `love.touchreleased` never, and `love.touch.getTouches()` still holds one id. On an iPad, put a finger on the game and pull down Control Center.

The fix is to add `case SDL_EVENT_FINGER_CANCELED:` beside the other three at line 396; the code after it already handles it.

What Lota does: ends the touch, as LÖVE's code shows it means to, without patching LÖVE. Lota sets an SDL event filter when it opens the event module (`ext/lota/native/event.cpp`), which SDL runs on each event as it is queued and which turns `SDL_EVENT_FINGER_CANCELED` into `SDL_EVENT_FINGER_UP`. `Event::convert` then makes `touchreleased` of it, in order with the other events, and `Touch::onEvent` removes the touch, so `Lota::Touch.touches` no longer lists it. `test/native/touch_test.rb` (`test_a_cancelled_finger_is_released_as_love_means`) holds it to that.

A second, smaller defect sits beside it: `Touch::getTouch` throws `love::Exception("Invalid active touch ID: %d", id)` with `id` an `int64` (`src/modules/touch/sdl/Touch.cpp`, line 70), which `%d` does not take, so the message is undefined behavior; on arm64 and x86_64 it prints the id's low 32 bits, which for an iOS finger id is not the id the game passed. The fix is `%lld` with a cast to `long long`, or `PRId64`.
