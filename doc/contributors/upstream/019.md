# On iOS 27, a game launched in landscape gets a portrait window

At the pinned LÖVE commit, `b7daef0f7`, with SDL 3.4.10, the SDL in love-apple-dependencies at `a5522634f1` (its newest commit on 2026-11-08) and the one Lota builds with `rake ios:sdl3`. LÖVE's `main` at `def245102c` (2026-11-05) has the same `src/common/ios.mm` and `platform/xcode/ios/love-ios.plist`. Written as the report we would file; LÖVE accepts none made with generative AI (AGENTS.md, "Reporting upstream"), and SDL asks that generative AI not be used in contributing to it, so it stays here. SDL has fixed it in its own repository (below), so there is nothing new to tell SDL; LÖVE has not yet taken an SDL with the fix.

On iPadOS 27, a game launched with the iPad in landscape draws a portrait-shaped picture: cut off at the bottom, with black on the right. Turning the iPad stretches the picture, and going home and back puts it right.

## What happens

iOS 27 makes `-[UIApplication statusBarOrientation]` a no-op: it answers `UIInterfaceOrientationUnknown` (0) and logs `-[UIApplication statusBarOrientation] API has been deprecated and is a no-op on 27.0 and later.` The iPhoneOS 27.2 SDK still declares it, deprecated since iOS 13 ("Use the interfaceOrientation property of the window scene instead", `UIKit.framework/Headers/UIApplication.h`, line 119). SDL 3.4.10 reads the interface orientation only from it:

- `src/video/uikit/SDL_uikitvideo.m`, line 240, in `UIKit_ComputeViewFrame`. Unknown is not landscape, so for a window that fills the screen and is wider than tall, and an app that supports portrait, it swaps the frame's width and height (lines 241 to 251). `UIKit_UpdateWindowBorder` sets the view's frame from it when a window goes fullscreen (`SDL_uikitwindow.m`, line 290), and so do `SDL_uikitwindow.m`, line 65, `SDL_uikitviewcontroller.m`, line 619, and `SDL_uikitopengles.m`, line 118.
- `src/video/uikit/SDL_uikitmodes.m`, line 333, in `UIKit_IsDisplayLandscape`, which orients the main screen's desktop mode (`UIKit_AddDisplay`, line 209) and its fullscreen modes (`UIKit_GetDisplayModes`, line 373), and refuses a landscape mode (`UIKit_SetDisplayMode`, lines 418 to 426).
- `SDL_uikitmodes.m`, lines 487 and 521, in `SDL_OnApplicationDidChangeStatusBarOrientation`, which turns the desktop and fullscreen modes to match and sends `SDL_EVENT_DISPLAY_ORIENTATION`, `SDL_ORIENTATION_UNKNOWN` for Unknown. `UIKit_InitModes` calls it (line 356), and so does `UIApplicationDidChangeStatusBarOrientationNotification` (`SDL_uikitevents.m`, lines 65 to 68 and 107 to 110).
- `src/video/uikit/SDL_uikitappdelegate.m`, lines 70 and 210, which choose a launch image, and `src/camera/coremedia/SDL_camera_coremedia.m`, lines 241 and 472, which turn a camera's frames.

SDL's `main` replaced all of these with `UIKit_GetInterfaceOrientation`, which on iOS 27, built with the iOS 27 SDK, reads the active window scene's `effectiveGeometry.interfaceOrientation`, and adds the scene delegate's `windowScene:didUpdateEffectiveGeometry:` to report a turn: commit `114aca1727c7` ("Fix for iOS 27 no op on statusBarOrientation", pull request 16355, for issue 16330). Commit `22a4d8b25eb1` ("Fixed window orientation on iOS 27", for issue 16436) then stopped `UIKit_ComputeViewFrame` from swapping at all on iOS 13 and newer, where the window's bounds already match the interface orientation, which a scene may not know yet at launch; made `UIKit_IsDisplayLandscape` fall back to the screen's bounds and `SDL_OnApplicationDidChangeStatusBarOrientation` wait while it is Unknown; and corrected the SDK test, which read `27000` for `270000`. SDL 3.4.20 carries both (`SDL_uikitvideo.m`, lines 249 and 270 to 286, at `release-3.4.20`); 3.4.18 has neither.

LÖVE's iOS build meets the same SDL code. Its `main` is SDL's (`src/love.cpp`, line 30, includes `SDL3/SDL_main.h`, so `main` becomes `SDL_main` and SDL's runs `SDL_RunApp`), which calls `UIApplicationMain` with no principal class (`SDL_uikitappdelegate.m`, line 60). `love-ios.plist` names no `NSPrincipalClass`, so the app's class is UIKit's own, and neither it nor `src/common/ios.mm` does anything about orientation. love-apple-dependencies' `SDL3.xcframework` is SDL 3.4.10, built against the iOS 26.4 SDK (`vtool -show-build`), and its iOS binary names the `statusBarOrientation` selector and not `effectiveGeometry`.

## To reproduce

Build a Lota game, or LÖVE's iOS app, against SDL 3.4.10 and run it on iPadOS 27 with the iPad held in landscape, with an `Info.plist` that allows portrait, as both apps' do. Any game window qualifies while the app fills the screen: `UIKit_ComputeViewFrame` compares the bounds of SDL's `UIWindow` with the screen's (`SDL_uikitvideo.m`, lines 227 to 243), not the window's fullscreen flag. An app iPadOS shows in a smaller window is spared. A game's own build saw it on an iPad Pro 12.9-inch (6th generation) with iPadOS 27.2 (24B119), built with Xcode 27.2 against the iphoneos27.2 SDK: in a scene-based app (`SDLUIKitSceneDelegate`) `statusBarOrientation` answered 0 on every call, while the window scene's `interfaceOrientation` was right. SDL's issue 16436 shows the same in the iPad Air 11-inch (M4) Simulator of iPadOS 27.0: `SDL_GetWindowSize` 820 by 1180 in landscape, and no `SDL_EVENT_WINDOW_RESIZED` after.

It has not been reproduced with Lota's own host. The Mac Lota is built on has Xcode 27.2 but only an iOS 26.1 Simulator runtime, and Lota's CI builds with Xcode 26.3 and runs iOS 26.2 Simulators, where `statusBarOrientation` still answers. Whether iOS 27 keys the no-op to the SDK an app links against or applies it to every app is not known; the log line names only the OS, and the device above ran an app built with the iOS 27 SDK.

## A fix

Take SDL 3.4.20 or newer, built against the iOS 27 SDK so that `UIKit_GetInterfaceOrientation` reads the window scene. Without that, an app can give UIKit a `UIApplication` subclass whose `statusBarOrientation` answers the window scene's orientation when UIKit's answers Unknown.

## What Lota does

Lota's iOS host does the second, since SDL's version is LÖVE's (`tasks/ios_build.rb`) and no patch to SDL is needed. `Host/Info.plist` names `LotaApplication` as `NSPrincipalClass`, and `Host/main.m` defines it (`ext/lota/phone/host/ios`). Its `statusBarOrientation` returns UIKit's answer, unchanged, whenever that is not Unknown, so nothing changes where the property still works, before iOS 27 or if iOS 27 keeps it working for apps built with older SDKs. When it is Unknown, it returns the `effectiveGeometry.interfaceOrientation` of the app's window scene, the connected `UIWindowScene` in the application role (iOS 16 and newer). With the same change in its own host, the game above drew 2732 by 2048 pixels in landscape and 2048 by 2732 in portrait on that iPad. `test/tasks/phone_host_test.rb` holds the class, its order, and the plist's key in place.

Still open: SDL 3.4.10 learns of a turn from `UIApplicationDidChangeStatusBarOrientationNotification`, and whether iOS 27 still posts it is not known. If it does not, the window still follows the turn, since the view controller lays the view out again, but the display modes keep their launch orientation and the game hears no `Lota.displayrotated`. And if a scene's orientation is itself still Unknown when SDL first asks, as SDL's issue 16436 supposes, Lota's host answers Unknown too and SDL swaps as before. Neither was seen on the iPad above. Both need a device or a Simulator of iPadOS 27 to check.
