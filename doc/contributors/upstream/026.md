# On iOS, Core Audio's decoder reads from the wrong place in the file

At the pinned LÖVE commit, `b7daef0f7`. Written as the report we would file; LÖVE accepts none made with generative AI (AGENTS.md, "Reporting upstream"), so it stays here.

LÖVE's iOS build decodes sound through Core Audio as well as its own decoders, so that an iOS game can load AIFF and AAC in an `.m4a` file. At this commit it loads neither. An M4A fails with "No suitable audio decoders found", and an AIFF either fails or comes out as a fraction of a second of noise from a decoder that mistook it for something else.

## What happens

The liblove-ios target compiles `src/modules/sound/lullaby/CoreAudioDecoder.cpp` and defines `LOVE_SUPPORT_COREAUDIO` (`platform/xcode/liblove.xcodeproj/project.pbxproj`, line 4994, and lines 5691-5694, 5717-5720, and 5743-5746), so `Sound::newDecoder` tries `CoreAudioDecoder` after Vorbis and before MP3 (`Sound.cpp`, lines 76-78). Its constructor opens the file with `AudioFileOpenWithCallbacks` (`CoreAudioDecoder.cpp`, line 66), whose read callback is given the byte offset to read from, `inPosition`. Audio File Services reads where it chooses: a header, then a chunk table, then packets, at offsets that are not one after another.

`readFunc` (lines 38-45) ignores `inPosition` and reads from wherever the Stream is:

```cpp
static OSStatus readFunc(void *inClientData, SInt64 inPosition, UInt32 requestCount, void *buffer, UInt32 *actualCount)
{
	auto stream = (Stream *) inClientData;
	int64 readbytes = stream->read(buffer, requestCount);
	...
```

So every read after the first returns bytes from the wrong offset, and Core Audio cannot parse the file. The callback honoured `inPosition` until commit `c09fef8e7` ("Audio source decoding improvements", 2022-04-21) moved decoders from a `Data` to a `Stream`: the old one copied from `data->getData() + inPosition`, and the new one dropped the offset.

## To reproduce

On a Mac, make the two files from one of macOS's own sounds:

```sh
cp /System/Library/Sounds/Ping.aiff ping.aiff
afconvert -f m4af -d aac ping.aiff ping.m4a
```

`afinfo` gives both as 2 channels at 48000 Hz, 1.50 s long. Put them in an iOS game and decode each with `love.sound.newSoundData`. On an iPhone 12 mini with iOS 27, a Lota build whose engine compiles `CoreAudioDecoder.cpp` with `LOVE_SUPPORT_COREAUDIO`, as liblove-ios does, gave:

```
decoded ping.aiff at 22050 Hz, 2 channels, 0.07 s
could not decode ping.m4a: No suitable audio decoders found.
```

The same build, with one change to `readFunc`, gave both files as `afinfo` describes them:

```
decoded ping.aiff at 48000 Hz, 2 channels, 1.5 s
decoded ping.m4a at 48000 Hz, 2 channels, 1.5 s
```

The iOS 26 Simulator gives the first pair as well.

## A fix

Seek to `inPosition` before reading, and report a failed seek as Audio File Services expects:

```cpp
	auto stream = (Stream *) inClientData;
	if (!stream->seek(inPosition))
		return kAudioFilePositionError;
	int64 readbytes = stream->read(buffer, requestCount);
```

That is the change the device ran.

## What Lota does

`readFunc` is static in `CoreAudioDecoder.cpp`, and `Sound::newDecoder` builds the decoder from LÖVE's own Stream, so nothing in Lota's own code can choose where the callback reads. Lota's iOS engine compiles the decoder with `LOVE_SUPPORT_COREAUDIO`, as liblove-ios does, and with a patch, `ext/lota/engine/coreaudio.patch`, which makes the change above and also sets `*actualCount` to 0 when the seek fails (ADR 005). CMake applies it only for iOS, the one target that compiles the file. With the fix, the decoder sits where LÖVE puts it, ahead of LÖVE's MP3 decoder, and reads what it is asked to read. The iOS Simulator check in `.github/workflows/phones.yml` decodes both files and expects them at 48000 Hz.
