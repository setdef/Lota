# LÖVE's LZ4 does pointer arithmetic on a null pointer in every compress and decompress

At the pinned LÖVE commit, `b7daef0f7`, which bundles LZ4 1.8.0 (`src/libraries/lz4/lz4.h`, lines 94-96). Written as the report we would file; LÖVE accepts none made with generative AI (AGENTS.md, "Reporting upstream"), so it stays here.

`love::data::Compressor`'s LZ4 compressor calls `LZ4_compress_default`, or `LZ4_compress_HC` from level 9 (`src/modules/data/Compressor.cpp`, lines 74-78), and decompresses with `LZ4_decompress_fast` when the caller passes the decompressed size and it matches the header's, or `LZ4_decompress_safe` otherwise (lines 132-153). Each reaches pointer arithmetic on a null pointer:

- `LZ4_compress_default` and `LZ4_compress_fast_extState` call `LZ4_compress_generic` with `noDict` (`src/libraries/lz4/lz4.c`, lines 744-751 and 788-790), on a context whose `dictionary` is null and `dictSize` 0, and line 549 computes `dictionary + cctx->dictSize`: zero added to a null pointer.
- `LZ4_decompress_safe` calls `LZ4_decompress_generic` with `dictStart` null and `dictSize` 0 (line 1350), and line 1192 computes `dictStart + dictSize`: zero added to a null pointer again.
- `LZ4_decompress_fast` calls it with `dictStart` null and `dictSize` 64 KB (line 1362), so line 1192 adds 65536 to a null pointer.

C11 leaves all three undefined (6.5.6, Additive operators). C2y defines the first two, adding zero to a null pointer (N3322), but not the third. No result is dereferenced, so a build without sanitizers runs correctly; the trouble is that UndefinedBehaviorSanitizer reports them. Its pointer-overflow check reports the first two in Apple clang 17, which is every Xcode on GitHub's macos-15 runner, and in LLVM clang 18, but not in Apple clang 21, which no longer reports zero added to a null pointer in C. It reports the third in all three.

To reproduce, compile `lz4.c` and `lz4hc.c` with `clang -fsanitize=undefined` (LLVM 18 or Apple clang 17) and call `LZ4_compress_default`, then `LZ4_decompress_safe` on its result: UBSan reports "applying zero offset to null pointer" at lines 549 and 1192. `LZ4_decompress_fast` on the same bytes reports "applying non-zero offset 65536 to null pointer" at line 1192 with any of the three compilers. In LÖVE, `love.data.compress("string", "lz4", "helloworld")` reaches the first, and `love.data.decompress("string", love.data.compress("data", "lz4", "helloworld"))` the third, since `w_decompress` passes a `CompressedData`'s own decompressed size (`src/modules/data/wrap_DataModule.cpp`, lines 158-162).

A fix would leave out the dictionary arithmetic when there is no dictionary, or update the bundled LZ4.

LZ4 fixed both statements itself. Its 8bea19d5 ("fixed minor cppcheck warnings in lib", in 1.9.0) computes `dictEnd` in `LZ4_decompress_generic` as `(dictStart == NULL) ? NULL : dictStart + dictSize` (`lib/lz4.c`, line 1426 there, line 1761 in 1.9.3), which covers `LZ4_decompress_fast`'s 64 KB as well as `LZ4_decompress_safe`'s 0, and its e68c7d38 ("avoid computing 0 offsets from null pointers", in 1.9.3) computes it in `LZ4_compress_generic` as `dictionary ? dictionary + dictSize : dictionary` (line 822 there, line 880 in 1.9.3).

What Lota does: `Lota::Data.compress` and `Lota::Data.decompress` call the same code, and Lota's own code cannot avoid the arithmetic, which is inside LZ4, so Lota compiles `lz4.c` with a patch of those two statements, backported from LZ4's two commits (`ext/lota/engine/lz4.patch`, applied by `ext/lota/engine/CMakeLists.txt`, ADR 001, section 2), and drops it when LÖVE bundles LZ4 1.9.3 or later. A dictionary that is not there still ends null, as the arithmetic left it, so LZ4 writes and reads the same bytes. `test/native/data_module_test.rb` compresses with both of LÖVE's LZ4 compressors and decompresses the result as a `CompressedData`, through `LZ4_decompress_fast`, and as bytes, through `LZ4_decompress_safe`, in the sanitized build that `rake test:native` runs (`ext/lota/CMakeLists.txt`, `LOTA_SANITIZE`). Without the patch, UBSan ends that run at line 1192 with Apple clang 21, and at line 549 with Apple clang 17, as on CI.
