# On Vulkan, a rebuilt swap chain with more images makes present throw "vector"

At the pinned LÖVE commit, `b7daef0f7`, and in love-android's `main` branch at `1c89bb0b2e` (2026-11-03), whose LÖVE 12 is a commit past `b7daef0f7` whose changes to `src/modules/graphics/vulkan/Graphics.cpp` touch none of the functions below. Written as the report we would file; LÖVE accepts none made with generative AI (AGENTS.md, "Reporting upstream"), so it stays here.

A game that LÖVE renders with Vulkan can fail in `love.graphics.present` with the error `vector` a few frames after LÖVE rebuilds its swap chain, if the new swap chain has more images than the first. On Android with vsync off it does, within a second of starting.

## What happens

The present of each swap chain image waits for a semaphore of that image: `submitGpuCommands` signals `renderFinishedSemaphores.at(imageIndex)` and `present` waits for it (`src/modules/graphics/vulkan/Graphics.cpp`, lines 499 and 608). `createSyncObjects` makes those semaphores, one for each image of the swap chain there is when it runs (lines 3577-3582), and `setMode` calls it once, when it creates the device (line 743). `recreateSwapChain` (lines 3685-3705) makes a new swap chain, and its images, but no semaphores. When the new swap chain has more images than the first, the first `vkAcquireNextImageKHR` that hands out an image past the old count leaves `imageIndex` past the end of `renderFinishedSemaphores`, and `std::vector::at` throws `std::out_of_range`, whose message, in libc++, is `vector`. Lua's error handler shows that, from `love.graphics.present`.

`createSwapChain` asks for `max(3, minImageCount)` images (lines 2123-2126), and a driver may give more than it asks for and change `minImageCount` from one swap chain to the next. On a OnePlus Nord N30 5G (Android 14, Adreno 619, Vulkan 1.1.128) with vsync off, where LÖVE picks `VK_PRESENT_MODE_MAILBOX_KHR` (lines 2299-2310), the surface reported a `minImageCount` of 3 before the window had a swap chain and 4 after, and the swap chains had 5 and then 6 images. The rebuild comes early: on the Nord, LÖVE rebuilt the swap chain at the end of its first present, which a request for a rebuild makes it do (lines 643-650).

## To reproduce

love-android's debug APK from its CI run 41632391450 (`app-normal-record-debug.apk`, at `1c89bb0b2e`), on the Nord above, with a game of two files:

```lua
-- conf.lua
function love.conf(t)
  t.window.width = 480
  t.window.height = 800
  t.window.vsync = 0
end

-- main.lua
local frame = 1
function love.draw()
  love.graphics.rectangle("fill", frame % 400, 100, 40, 40)
  print("frame " .. frame)
  frame = frame + 1
end
```

Zip them into `repro.love`, copy it into the app's files with `adb shell run-as org.love2d.android`, and open it with `adb shell am start -a android.intent.action.SEND -t application/octet-stream --eu android.intent.extra.STREAM file:///data/user/0/org.love2d.android/files/repro.love -n org.love2d.android/.IntentReceiverActivity`. LÖVE renders with Vulkan (`Vulkan / 1.1.128 / Qualcomm / Adreno (TM) 619`), and at the sixth frame:

```
I SDL/APP : [LOVE] Error: [love "callbacks.lua"]:201: vector
I SDL/APP : stack traceback:
I SDL/APP : 	[love "boot.lua"]:479: in function <[love "boot.lua"]:475>
I SDL/APP : 	[C]: in function 'present'
I SDL/APP : 	[love "callbacks.lua"]:201: in function <[love "callbacks.lua"]:175>
```

The error handler then crashes, which `doc/contributors/upstream/025.md` reports. With `t.window.vsync = 1` the same game ran 40 frames without an error; calling `love.window.setVSync(0)` at the 40th, which rebuilds the swap chain (line 3369), made the 45th throw. In landscape (800 by 600) with vsync off it ran without an error, because on Android LÖVE rebuilds its swap chain after every present there (`VK_SUBOPTIMAL_KHR`, lines 643-650), and a swap chain rebuilt every frame never hands out its last image.

Lota's build of LÖVE's engine, with logging added, showed the cause on the same phone: the first swap chain had 5 images and 5 semaphores, the one rebuilt at the end of the first present had 6, and `vkAcquireNextImageKHR` returned `imageIndex` 5 with 5 semaphores, on the frame that threw.

## A fix

Make the semaphores of a swap chain whenever LÖVE makes one. The smallest change makes those of the images a new swap chain adds, in `recreateSwapChain` after `createSwapChain`:

```cpp
for (size_t i = renderFinishedSemaphores.size(); i < swapChainImages.size(); i++)
{
	VkSemaphoreCreateInfo semaphoreInfo{};
	semaphoreInfo.sType = VK_STRUCTURE_TYPE_SEMAPHORE_CREATE_INFO;

	VkSemaphore semaphore = VK_NULL_HANDLE;
	if (vkCreateSemaphore(device, &semaphoreInfo, nullptr, &semaphore) != VK_SUCCESS)
		throw love::Exception("Failed to create image available semaphore");
	renderFinishedSemaphores.push_back(semaphore);
}
```

`cleanup` destroys them all, as before (lines 3598-3600), and a swap chain with fewer images leaves the rest unused.

## What Lota does

The semaphores and the swap chain are private to LÖVE's `Graphics`, and a game cannot choose how many images a driver gives a swap chain, so nothing in Lota's own code can do this. Lota compiles `vulkan/Graphics.cpp` with a patch, `ext/lota/engine/vulkan_semaphores.patch`, which adds the loop above, wherever it builds LÖVE's Vulkan renderer: on Linux, Windows, and Android.

Lota's Android patch, `vulkan_present.patch`, which takes a suboptimal present as a success so that a game in landscape does not rebuild its swap chain every frame, made this failure come in landscape too, as it does in portrait in LÖVE. A Lota game in landscape with vsync off threw `vector` from `Lota::Graphics.present` on the Nord at its sixth frame, whether it drew 10,000 rectangles a frame or 120,000. With the patch, the same game made a sixth semaphore when its swap chain was rebuilt with 6 images, handed out every image, and drew its frames to the end.
